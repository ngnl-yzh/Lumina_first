# 미리내

보이스피싱·딥보이스 대응 모바일 앱. Team Lumina · 전남대학교 인공지능학부.

**하나의 앱, 두 개의 모드.**
모드 1은 통화 중 사기범 발화를 실시간 분석해 경고하고,
모드 2는 녹음과 동시에 적대적 섭동을 주입해 딥보이스 학습을 막는다.

```
미리내/
  LUMINA-D07_최종계획서.html      계획서 (원본)
  LUMINA-D08_모드1_설계도.html    모드 1 설계도
  LUMINA-D09_모드2_설계도.html    모드 2 설계도
  server/        Python — PGD 코어 · 모드 1 스코어러 · WebSocket 서버
  app-desktop/   PC 버전 — **실제로 동작한다**
  app-mobile/    폰 버전 — UI 전용 (서버 없이 단독 실행)
```

앱이 두 개인 이유는 목적이 다르기 때문이다.

| | PC (`app-desktop`) | 폰 (`app-mobile`) |
|---|---|---|
| 목적 | 실제로 돌려서 확인·시연 | 최종 제품 형태를 보여준다 |
| 마이크 | AudioWorklet raw PCM | 안 쓴다 |
| 서버 | WebSocket 필수 | 필요 없다 |
| 데이터 | 진짜 전사·채점·섭동 | 대본 재생 |
| HTTPS | 불필요 (localhost) | 필요 (자체 서명 인증서) |

## 실행 방법은 두 가지

**① 배포본 (파이썬·노드 불필요)** — 시연 장비를 세팅하는 사람이 개발자가 아닐 때.
`미리내.exe`를 더블클릭하면 브라우저가 열리고 바로 쓸 수 있다. 만드는 법은 `BUILD.md`.

> **시연 전에 반드시 그 장비에서 한 번 실행할 것.**
> 모델(Whisper 등)은 EXE에 없고 첫 실행에 받는다. 현장에서 인터넷이 안 되면 아무것도 안 된다.

**② 소스 실행** — 개발하거나 실험 도구까지 쓸 때. 아래 순서를 따른다.

## 빠르게 실행

```bash
# 1) 서버
cd server
py -3.11 -m venv .venv && .venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python ws_server.py --port 8765

# 2-a) PC 버전 — 실제 동작
cd app-desktop
npm install && npm run dev          # http://localhost:5174

# 2-b) 폰 버전 — UI만
cd app-mobile
npm install && npm run dev:https    # 폰에서 https://<노트북IP>:5173
```

자세한 내용은 각 폴더의 README를 볼 것.

## 지금까지 확인된 것

**작동한다**

- PGD 코어 — 단위 테스트 47건 통과. gradient 검증 상대오차 8.1e-09
- 적대적 섭동이 같은 SNR 잡음 대조군보다 화자 임베딩을 더 무너뜨린다
- C-E(셔플 섭동) 대비 우위 — 효과의 원인이 크기가 아니라 **구조**임을 지지
- 모드 1 스코어링 — 8단계 182항, 경로별 정규화, 개입 판정. 서버 통합 테스트 통과
- PC 앱이 서버와 실제로 통신한다 (마이크 → WebSocket → 전사 → 채점 → 개입)
- 폰 앱 UI — 타입체크·빌드 통과

**실제 공개 녹취로 교차검증했다** — 자체 시나리오는 성능을 20%p 과대평가하고 있었다.

`eval/scenarios_real.json`은 사기 발화를 한 줄도 짓지 않는다. 전부 언론·판결·기관이
공개한 인용문이고 발화 단위로 출처를 붙였다.

| | 자체 작성 | **실제 공개 녹취** |
|---|---|---|
| 탐지율 | 81.2% | **60.0%** → (DB 보완 후) 80.0% |

미탐 2건이 전부 **대면편취형**이었다 — 현금을 찾아 사람에게 직접 건네게 하는 수법으로,
**전체 보이스피싱의 66.9%**를 차지한다. DB가 계좌이체 중심이라 주류 수법을 놓치고 있었다.
공개 자료를 근거로 5항(S4 물리적 고립 유도 · S5 대면편취)을 보완했다.

SBS가 공개한 **진짜 사기범 녹취**가 0.117 "안전"으로 완전히 미탐이었다는 점이 특히 아팠다.
자체 시나리오에서는 같은 녹취를 쓰면서 연결구에 "대포통장"·"안전계좌"를 내가 넣어
탐지되고 있었다. **시나리오를 직접 쓰면 자기도 모르게 정답을 흘린다.**

**가족 금융 대화 12건은 전부 통과했다.** 등록금·병원비·전세 계약금·경조사비·대출 갈아타기·
상속 — `계좌`·`이체`·`송금`·`급하게`가 정당하게 나오는 대화들이다.
형제에게 진짜로 돈을 빌리는 통화(지인 사칭과 표면 구조가 거의 같다)도 0.000이다.

**모드 1 탐지 성능** (시나리오 57건 · 사기 21 · 정상 36 · `server/eval_mode1.py`)

단위 테스트는 알고리즘 **구조**만 본다. 탐지 성능은 따로 재야 하고,
재현율만 재면 안 된다 — 무조건 "위험"이라 답해도 재현율은 100%가 된다.
그래서 사기 16건과 **정상 통화 24건**을 함께 넣고 오탐률을 같이 낸다.

| 지표 | 처음 | 지금 |
|---|---|---|
| 탐지율 | 80.0% | 81.0% [60.0, 92.3] |
| 정밀도 | 53.3% | **100.0%** [81.6, 100.0] |
| **오탐률** | **58.3%** | **0.0%** [0.0, 9.6] |
| 회피 성공률 | 33.3% | **16.7%** |
| 발화당 채점 (30번째 발화) | 60.7초 | **0.023초** |

수치는 **95% 신뢰구간(Wilson)과 함께** 읽어야 한다 — 정상 36건에서 오탐 0건이어도
실제 오탐률은 9.6%까지 가능하다. 그리고 아래 STT 오차 항목대로,
**전사에 오차가 끼면 점 추정 자체가 오른다.**

처음 측정에서 **정상 통화 12건 중 7건이 위험으로 떴다.** 단위 테스트 47건은
전부 통과한 상태였다. 원인 세 가지 모두 에러 없이 조용히 틀리는 종류였다 —
자모 근사매칭이 음절 경계를 넘어 유령 표현을 만들고("담**당자**입"에서 "당장"이
편집거리 0으로 검출), 인용과 지시를 구별하지 못하고(**앱이 띄운 경고를 사용자가
읽으면 앱이 자기 경고에 반응했다**), critical 하한이 정상 문맥 감점을 덮어썼다.

그 뒤 **우리가 넣은 규칙을 우리가 공격했다**(`eval/scenarios_evasion.json`).
예방 교육 오탐을 막으려던 수정이 회피 통로였음이 드러났다 —
사기범이 예방 문구를 여섯 개 흘리자 C1·C2·P1이 모두 발동한 통화가
**0.000 "안전"**으로 나왔다. 가정이 아니라 SBS 공개 녹취에 나오는 실제 수법이다.

자세한 내용과 남은 한계는 `server/README.md`에 있다.

**주의 — 오탐률 0%는 깨끗한 전사에서만 성립한다.**
STT 오차 10%를 주입하면 탐지율 70.8% · 오탐률 3.8%로 내려간다.
발표에서 0%만 말하면 거짓말이 된다.

**안 된다 — 가장 중요한 것**

**XTTS-v2 복제를 막지 못한다.** 계획서가 UI보다 먼저 닫으라고 못박은 관문이고,
시연 영상의 클라이맥스다. 세 가지 방식(전이 · 화이트박스 · 이중 경로)을 시도했고
n=5 반복 측정으로 확인했다.

| 조건 | n | 평균 SRS | 95% CI |
|---|---|---|---|
| 원본 (기준선) | 5 | 0.9524 | ±0.0041 |
| **보호본** | 5 | **0.9122** | ±0.0151 |
| C-B 대역제한잡음 | 5 | **0.8566** | ±0.0172 |

방어 효과 자체는 실재한다(원본과 보호본의 CI가 겹치지 않는다).
그러나 **같은 SNR의 단순 잡음이 적대적 섭동보다 유의하게 더 복제를 방해한다.**
적대적 최적화의 이점이 이 모델에서는 나타나지 않는다.

**C-D(타 화자) 대조군을 확보해 이 수치들을 해석할 기준을 만들었다.**
그전까지는 "SRS 0.63이 좋은 건가"에 답할 수 없었다 — 남남의 SRS를 몰랐기 때문이다.
XTTS 내장 화자 6명으로 두 분포를 같은 조건에서 쟀다(`calibrate_dsr.py`).

| 분포 | 조각쌍 | 평균 |
|---|---|---|
| 같은 화자 | 116 | 0.8622 ±0.0331 |
| 타 화자 (C-D) | 664 | 0.5962 ±0.0944 |

→ **EER 임계값 0.7962 · 동일오류율 4.3%.** 근거 없이 쓰던 0.75를 이 값으로 교체했다.

이 기준으로 보면 두 단계의 대비가 선명해진다.

| 단계 | 보호본 SRS | 판정 |
|---|---|---|
| **인코더** (섭동이 공격하는 대상) | 0.6342 | 타 화자 ✓ (C-B 0.769 · C-E 0.890보다 낮다) |
| **복제** (실제로 막아야 하는 것) | 0.9122 | **같은 사람 — DSR 0%** |

**인코더는 무너뜨렸지만 복제는 못 막았다.** 이제 그 문장이 근거 있는 임계값을 가진다.
제로샷 복제 모델이 화자 임베딩 하나로 음색을 결정하지 않는다는 뜻이다.

**그리고 통화 채널을 통과시키자 인코더 단계 성공마저 사라졌다.**
미리내는 전화 통화용인데 지금까지의 모든 SRS는 파일 대 파일로 잰 값이었다.
`codec.py`(300~3400 Hz · 8 kHz · G.711)를 통과시키니 보호본이 0.6342 → **0.8346**,
판정 임계값 위로 되돌아왔다. 잡음 대조군은 오히려 채널 통과 후 더 잘 막았다.

원인은 코덱이 아니었다 — 섭동은 그대로 남아 있었다(잔존 101% · 구조 상관 0.989).
섭동이 **전대역 원본**을 표적으로 최적화되는데 상대는 채널 통과본을 듣는다.
**표적이 틀렸던 것이다.**

`PGDConfig.channel_aware`로 손실을 `encoder(channel(x+δ))` 대 `encoder(channel(x))`로
바꾸고 진짜 코덱으로 검증했다.

| | 깨끗한 파일 | **통화 채널 통과 후** |
|---|---|---|
| 기존 | 0.6342 | 0.8346 ✗ |
| **채널 인지** | 0.9429 | **0.5915** ✓ |

채널 통과 후 C-B(0.662)·C-A(0.746)·C-E(0.857)를 모두 이긴다 —
**통화 경로에서 적대적 섭동이 잡음을 이긴 것은 이번이 처음이다.**

자세한 시도 기록과 진단은 `server/README.md`의 "C-D 대조군"·"복제 게이트" 절에 있다.

**딥보이스 탐지(P1)도 못 쓴다.** 사전학습 탐지기가 XTTS-v2 합성음 16개 중 3개만 잡았고
(재현율 18.8%), 같은 조건에서 만든 5개가 1.0000과 0.0000으로 갈리는 양극단 분포였다.
D08이 예고한 "학습에 없던 합성 방식에 일반화가 약하다"가 그대로 나왔다.
코드는 남기되 기본값을 끄고, 켜더라도 위험도 점수는 바꾸지 않게 했다.

## 발견한 설계 결함

구현하면서 설계도의 결함 4건을 찾았다. 넷 다 **에러 없이 조용히 틀리는** 종류다.

| # | 위치 | 내용 |
|---|---|---|
| 1 | D09 PGD | 정규화 순서 — 루프 밖에 두면 마스킹 제약이 깨진다 (D02가 이미 지적) |
| 2 | D09 투영 | `D/abs(D)` 0-나눗셈 NaN이 ISTFT로 번진다 (D02가 이미 지적) |
| 3 | D09 PGD | **`delta = zeros_like(x)`는 정류점이다.** gradient가 δ=0에서 1.0e-07, 랜덤 초기화에서 4.1e-01 — 6자릿수 차이. 22.8%의 샘플은 `sign(0)=0`이라 아예 안 움직인다 |
| 4 | D08·D09 모듈표 | **MediaRecorder로는 이 파이프라인이 안 된다.** 손실 압축이 섭동을 지운다 — 코덱과 마스킹이 같은 원리라서 그렇다. AudioWorklet raw PCM으로 교체 |

추가로 D03이 지정한 자모 근사매칭 임계값 0.34가 중간 길이 표현에서 오탐을 낸다.
정상 발화 "오늘 날씨가"가 S6 키워드 "오늘까지"에 매칭됐다. 편집 허용치를 2로 묶어 해결.

## 문서 정합성 — 고쳐야 할 것

D07 §08이 이미 개정 목록을 갖고 있다. 여기에 구현에서 나온 것을 더한다.

| 문서 | 현재 서술 | 고칠 내용 |
|---|---|---|
| D08 §06 · D09 §5.1 | `recorder.js` — MediaRecorder API | **AudioWorklet raw PCM** (위 결함 4) |
| D09 §04 의사코드 | `delta = zeros_like(x)` | 랜덤 초기화 (위 결함 3) |
| D09 §6.2 | `abs(stft(δ)) ≤ thr×ratio` 단언 | STFT 투영만으로는 성립하지 않는다. 강제 옵션과 실측 초과량 병기 |
| D09 §05 | 마스킹 배율 0.75 잠정 | **실측 확정** — 0.75는 잡음보다 나쁘다(0.892 vs 0.715). 1.5는 판정 불가(구간 겹침). 3.0부터 유의하게 우세. **안 들리면서 잡음을 이기는 지점은 없다** |
| D09 §01 | XTTS conditioning "비공개 · 최대 리스크" | **가중치 공개. 화이트박스 접근 가능.** 경로가 둘(speaker_encoder · gpt_cond)이다 |
| R02 3.2 · R05 5.1 · R05 4.4 · R01 8.3 | — | D07 §08 목록 그대로 |

**이번 구현·측정에서 추가된 개정 항목** (전부 실측 근거가 코드 주석과 `server/README.md`에 있다)

| 문서 | 현재 서술 | 고칠 내용 |
|---|---|---|
| D09 §06 지표 | 가청도 = `audibility(δ, thr, ratio)` | **배율마다 기준선이 달라 배율 간 비교에 못 쓴다.** 절대 기준(thr×1.0)을 함께 낼 것. 실측 예: 같은 파일이 제약 기준 2.44% vs 절대 기준 **20.30%** |
| D09 §04 손실 | `E(x+δ)` 대 `E(x)` | **통화 채널을 표적에 포함**해야 한다. 파일 기준으로 최적화하면 채널 통과 시 방어가 임계값 위로 되돌아온다(0.634 → 0.835). `channel_aware` |
| D09 §06 DSR | 판정 임계값 미정 | **C-D 대조군으로 확정** — EER 0.7962 · 동일오류율 4.3%. 근거 없던 0.75를 교체 |
| D08 §02 패턴 DB | 8단계 72개 표현 · 변형 포함 182개 | **77 · 198.** 실제 공개 녹취 교차검증으로 5항 추가(S4 물리적 고립 유도 3 · S5 대면편취 2). **대면편취형이 전체의 66.9%인데 DB가 이체 중심이었다** |

## 평가 절차 주의

패턴 DB(`server/mirinae/mode1/pattern_db.json`)와 **평가 시나리오는 작성자를 분리해야 한다.**
같은 주체가 둘 다 만들면 탐지율이 인위적으로 높아지고 코드로는 막을 수 없다(D08 §07).
현재 DB는 초안이며 금융감독원 공개 재연 자료로 교차 검증이 필요하다.
`server/tests/test_mode1.py`는 **알고리즘 구조 테스트**이지 탐지율 평가가 아니다.
