# 미리내 · 서버 코어 (모드 2)

D09(모드 2 설계도)의 서버 측 구현. 모듈명은 D09 §5.1 명세와 일치시켰다.

계획서(D07 §04)가 못박은 순서를 따른다.
**① 오프라인 보호 파일 → ② 복제 실패 확인 → ③ 앱.** 현재 ①이 끝났고 ②가 남았다.

## 설치 — venv 두 개

의존성이 충돌해서 환경을 나눴다. coqui-tts가 numpy 2.x를 끌어오는데
PGD 코어는 numpy<2.0에 고정되어 있다. 한 환경에 두면 둘 중 하나가 깨진다.
`clone_test.py`가 subprocess로 XTTS venv를 호출하므로 섞을 필요도 없다.

```bash
# ① 메인 — PGD 코어
py -3.11 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt

# ② XTTS — 복제 검증 전용
py -3.11 -m venv .venv-xtts
.venv-xtts\Scripts\python -m pip install -r requirements-xtts.txt
```

RTX 3060 장비에서는 양쪽 torch를 CUDA 빌드로 설치한다.

```bash
pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu121
```

코드는 device를 자동 판별한다. 두 가지 함정이 있어 requirements에 적어 뒀다.

- `setuptools<81` 핀 필수 — resemblyzer→webrtcvad가 `pkg_resources`를 쓰는데 81+에서 제거됐다.
- `coqui-tts`는 **torch를 자동으로 끌어오지 않는다.** 별도로 설치해야 한다.

## 사용

```bash
# 보호 파일 생성
python protect.py 목소리.wav -o out/
python protect.py --synth --steps 20 -o out/       # 음성 없이 배관만 확인

# 파라미터 스윕 (마스킹 배율 확정용)

# 복제 실패 검증 — D1~D2 게이트
python clone_test.py out/original.wav out/protected.wav

# 단위 테스트 20건
python -m pytest tests -q
```

팀원 녹음이 아직 없을 때 배관만 뚫어보려면 XTTS 내장 화자로 참조 음성을 만든다.
**이 경로로 얻은 수치는 결과가 아니다** — 대상 음성 자체가 XTTS 산물이라
복제가 유난히 쉬운 조건이다.

```bash

python protect.py out/reference.wav -o out/ref

```

## 구현 중 발견해 고친 결함

D02 검토가 짚은 2건에 더해 3건을 추가로 찾았다. 다섯 다 **에러 없이 조용히 틀리는** 종류다.
(4·5번은 아래 "C-D 대조군" 절에서 자세히 다룬다)

1. **정규화 순서** (D02 지적) — 정규화를 루프 밖에 두면 마스킹 제약이 깨진다. 루프 안·투영 앞으로 배치.
2. **투영식 0-나눗셈** (D02 지적) — 무음 구간 NaN이 ISTFT로 번진다. `where(mag > 1e-12, ...)`로 수정.
3. **δ 초기화** (신규) — D09 의사코드의 `delta = zeros_like(x)`는
   cos_sim = 1인 **정류점**에서 출발한다. 실측 gradient 크기가
   δ=0에서 `1.0e-07`, 랜덤 초기화에서 `4.1e-01`로 6자릿수 차이가 났고,
   δ=0에서는 전체 샘플의 **22.8%가 gradient 정확히 0**이라 `sign(0)=0`으로 움직이지도 않는다.
   첫 스텝 방향이 사실상 float32 반올림 오차로 정해진다. 표준 PGD대로 랜덤 초기화로 교체.

## 설계도와 달라진 점

두 가지는 D09 원문대로 구현할 수 없었다. 숨기지 않고 계측해서 남긴다.

**① 마스킹 불변식이 하드 투영만으로는 서지 않는다.**
STFT 도메인에서 크기를 깎은 스펙트로그램은 대개 일관적이지 않다 —
그런 STFT를 갖는 시간축 신호가 존재하지 않는다. ISTFT를 거치면 overlap-add로
에너지가 번져 일부 bin이 다시 임계값을 넘는다.
실측: 투영만으로는 200회를 반복해도 최대 초과 +8 dB 수준에서 수렴.
→ `PGDConfig.enforce_masking=True`면 전역 축소로 불변식을 **강제**한다
(안 들림이 보장되는 대신 방어가 약해진다). 기본값은 False이며
초과량을 `metrics.audibility`로 정직하게 보고한다. 어느 쪽을 쓸지는 청취 평가로 결정.

**② 대역 밖 에너지가 −52 dB로, 목표 −60 dB에 못 미친다.**
루프 안 단일 청크에서는 −60 dB 아래를 만족한다(테스트 통과).
전체 파형에서 −52 dB가 되는 이유는 D09가 지정한 연산 순서
`bandpass(delta) * fade(vad)` 때문이다 — 대역 제한 **뒤에** 마스크를 곱하므로
시간축 곱셈이 주파수축 확산을 일으킨다. 순서를 뒤집으면 마스크 경계가 필터에 뭉개져
클릭음 위험이 돌아온다. 현재는 설계도 순서를 지키고 −52 dB를 그대로 보고한다.

## 마스킹 배율 — 트레이드오프 곡선 (n=5 · 실제 음성)

D09가 "청취 평가로 결정"하도록 열어둔 **유일한 미확정 파라미터**다.
한때 조건당 1회, 합성 신호로 재고 배율 3.0을 잠정 확정했다. 그 근거를 다시 세웠다.

```bash
python sweep_params.py out/reference.wav --repeat 5 --steps 50 \
       --ratios 0.75,1.5,3.0,6.0,10.0 --offset-sec 1.0
```

기준선: C-A 백색잡음 0.7832 ±0.0070 · **C-B 대역제한잡음 0.7146 ±0.0110** (이겨야 할 값)

| 배율 | SRS (n=5) | 대조군 대비 | 절대 초과 dB | **위반 bin %** | 제약 초과 dB |
|---|---|---|---|---|---|
| 0.75 | 0.8924 ±0.0138 | ✗ 대조군보다 나쁨 | 12.0 | **0.44%** | 14.5 |
| 1.50 | 0.7296 ±0.0123 | **? 우위 미확인** | 15.3 | 17.78% | 11.8 |
| 3.00 | 0.4907 ±0.0114 | ✓ +0.224 | 22.9 | 23.45% | 13.3 |
| 6.00 | 0.3255 ±0.0037 | ✓ +0.389 | 27.7 | 24.48% | 12.2 |
| 10.00 | 0.2681 ±0.0063 | ✓ +0.446 | 29.7 | 24.28% | 9.7 |

**① 배율 0.75에서는 적대적 섭동이 잡음보다 못하다.**
D09가 기록한 "선행연구 권장 0.75에서 자체 실험 DSR 0%"가 실제 음성·n=5에서 재현됐다.

**② 배율 1.5는 "우위 없음"이 아니라 "구별 못 함"이다.**
점 추정은 대조군보다 0.015 낮지만 신뢰구간이 겹친다. n=5로는 판정할 수 없다는 뜻이고,
둘을 같은 말로 쓰면 표본이 부족한 실험이 결론으로 둔갑한다.

**③ 그리고 이것이 핵심이다 — 안 들리면서 잡음을 이기는 지점이 없다.**

| 배율 | 들리는가 | 잡음을 이기는가 |
|---|---|---|
| 0.75 | 거의 안 들림 (위반 0.44%) | **아니오** |
| 1.50 | 이미 들림 (17.8%) | 판정 불가 |
| 3.00+ | 뚜렷이 들림 (23~24%) | 예 |

위반 비율이 배율 0.75 → 1.5 구간에서 **0.44% → 17.8%로 40배** 뛴다.
대조군을 이기는 최소 지점(3.0)에서는 이미 bin의 23%가 마스킹 임계값을 넘는다.
**"안 들린다"와 "잡음보다 낫다"를 동시에 만족하는 설정이 이 범위에 없다.**
청취 평가가 정할 것은 배율이 아니라 **어느 쪽을 포기할지**다.

> 절대 초과와 제약 초과를 구별해서 읽을 것 — 제약 초과 열은 배율이 커질수록
> 오히려 줄어든다(14.5 → 9.7). 그것만 보면 정반대 결론이 나온다. 아래 "결함 5" 참조.

파이프라인 실행 (6초 · 5청크 · 20스텝 · 배율 3.0):

```
적대적 섭동 (미리내)  0.6767      C-C 무섭동     1.0000
C-A 백색잡음         0.7628      C-E 셔플 섭동   0.9546
C-B 대역제한잡음      0.7429
```

C-E가 0.955로 거의 무효인 반면 최적화된 섭동은 0.677 —
**효과의 원인이 크기가 아니라 구조**임을 지지한다. 발표에서 가장 강한 카드다.
C-C가 정확히 1.0000인 것은 인코더가 정상 동작한다는 확인이다.

## 모바일 전용 — 클라이언트 쪽에 걸리는 것

앱은 모바일 전용(PWA)이다. 서버 코어 쪽에는 영향이 없지만
클라이언트 명세에 고쳐야 할 것이 하나 있다.

**D08·D09가 지정한 `MediaRecorder API`로는 이 파이프라인을 못 돌린다.**

MediaRecorder는 **압축된** 오디오를 낸다. iOS Safari는 audio/mp4(AAC),
Chrome은 WebM/Opus다. 우리에게 필요한 건 16 kHz 모노 **raw PCM**이고, 이유가 두 가지다.

- 모드 2는 overlap-add로 섭동을 샘플 단위로 정렬해 합친다. 압축을 거치면 정렬이 깨진다.
- 더 중요하게, 손실 압축은 우리가 SNR 20 dB로 정밀하게 넣은 섭동을 **그 자리에서 지운다.**
  코덱은 정확히 "안 들리는 성분"을 버리도록 설계되어 있는데, 섭동이 바로 그 성분이다.
  심리음향 마스킹 아래로 숨긴 신호와 심리음향 코덱은 같은 원리로 만들어졌다.

→ `recorder.js`는 **Web Audio API의 AudioWorklet**으로 raw Float32 PCM을 직접 받아야 한다.
   MediaRecorder는 쓰지 않는다. D08 §06 모듈표와 D09 §5.1 모듈표를 함께 고칠 것.

그 외 모바일 전용이라 확인해야 하는 것들:

| 항목 | 내용 |
|---|---|
| HTTPS 필수 | 마이크·AudioWorklet 모두 secure context 필요. 시연은 자체 서명 인증서 또는 터널 |
| 사용자 제스처 | iOS는 탭 없이 오디오 컨텍스트가 시작되지 않는다 |
| 화면 꺼짐 | 녹음 중 화면이 꺼지면 처리가 끊긴다. Wake Lock API 필요 |
| 노치·홈바 | `viewport-fit=cover` + `safe-area-inset` |
| PWA 셸 | manifest · service worker · `display: standalone` |
| 현재 목업 | `App.tsx`의 `Phone` 컴포넌트는 데스크톱에서 폰을 흉내낸 베젤+가짜 상태바다. 실기기에서는 제거하고 전체 뷰포트를 쓴다 |

D07 리스크표가 이미 SEV2로 잡아둔 "폰 브라우저 마이크 제약"이 이 항목들이다.
계획서대로 **D1에 실기기에서 먼저 확인**한다.

## 모드 1 탐지 성능 — 측정하고 고쳤다

`tests/test_mode1.py`는 **알고리즘 구조 테스트**이지 탐지율 평가가 아니다.
"테스트 47건 통과"가 "잘 잡는다"로 읽히는 것을 막으려고 평가를 따로 만들었다.

```bash
python eval_mode1.py                 # 탐지율 + 오탐률
python eval_mode1.py -v              # 실패 케이스 근거
python eval_mode1.py --gaps          # 미탐 원인을 DB 공백 관점에서
python eval_mode1.py --compare out/eval_baseline.json   # 개선 전후
```

**재현율만 재면 안 된다.** 무조건 "위험"이라고 답해도 재현율은 100%가 된다.
그래서 `eval/scenarios.json`은 사기 10건과 **정상 통화 12건**을 함께 담는다.
정상 통화가 평가의 절반이다.

### 처음 재봤더니

| 지표 | 값 |
|---|---|
| 탐지율 | 80.0% |
| **오탐률** | **58.3%** |
| 정밀도 | 53.3% |

**정상 통화 12건 중 7건이 "위험"으로 떴다.** 실사용이 불가능한 수준이다.
단위 테스트 47건은 전부 통과한 상태였다 — 구조 테스트로는 이게 안 잡힌다.

### 원인 세 가지, 전부 조용히 틀리는 종류였다

**① 자모 근사매칭이 음절 경계를 무시했다.**
자모 문자열 위를 1칸씩 미끄러지므로 "담당자입니다"의 자모 안에서
"당장"(`ㄷㅏㅇㅈㅏㅇ`)이 **편집거리 0으로** 발견된다.
"자입"의 `ㅈㅏ` 뒤에 "입"의 초성 `ㅇ`이 붙어 생긴 유령이라 임계값으로는 못 막는다.
정상 통화 12건에서 이런 **유령 매칭이 31건** 나왔다.

| 잡힌 키워드 | 실제 원문 |
|---|---|
| 송금 | "조금 전", "등록금", "궁금하신" |
| 당장 | "담**당자**입니다" |
| 실형 | "조**심해**야 돼" |
| 경찰청 | "경찰**서** 수사과" |

→ 창을 **음절 경계에 정렬**하고, **4음절 미만은 근사매칭을 끄고**,
**초성 시퀀스로 먼저 거른다**(STT 오차는 대개 중성·종성에서 난다).
유령 매칭 31건 → 10건.

**② 인용과 지시를 구별하지 못했다.**
같은 문자열이라 패턴 매칭만으로는 가를 수 없다.

```
사기범   "안전계좌로 이체하세요."
피해자   "안전계좌로 이체하라고 했어요."          ← 1332 상담
자녀     "안전계좌로 이체하라는 말 나오면 끊어."   ← 예방 교육
앱 자신  "안전계좌라는 것은 존재하지 않습니다."    ← 미리내 경고문
```

마지막 줄이 특히 나빴다 — **앱이 띄운 경고를 사용자가 읽으면 앱이 자기 경고에 다시 반응한다.**

한국어는 인용을 어미로 표시하고 그 어미가 인용된 말 **뒤에** 온다.
매칭 구간 뒤 14음절만 보면 된다(`context.py`). 문법 분석기가 필요 없다.

부정 표현("없다·않다")은 **쓰지 않았다.** 사기범이 더 자주 쓴다 —
"오늘까지 처리하지 **않으면** 계좌가 동결됩니다"는 실제 사기 발화다.
부정을 억제 신호로 쓰면 이런 발화의 위험 단계가 통째로 지워진다.

**③ critical 하한이 정상 문맥 감점을 덮어썼다.**
`max(score, 0.75)`가 감점 **뒤에** 걸려서, benign 지시어가 몇 개 잡히든 결과가 0.75로 같았다.
감점이 계산에서 통째로 사라지고 있었다.

### 실시간성 — 발화당 비용이 통화 길이에 무관해졌다

발화마다 누적 버퍼 **전체를 다시 채점**하고 있었다. 통화가 길어질수록 비용이 선형으로 늘었다.

| 발화 번호 | 그 발화 채점 시간 |
|---|---|
| 1 | 0.85초 |
| 10 | 19.2초 |
| 30 | **60.7초** |

30분 통화에서는 개입이 통화가 끝난 뒤에 뜬다. 실시간이라고 부를 수 없었다.

버퍼는 뒤에만 붙으므로 앞쪽 판정은 바뀌지 않는다 — 다시 잴 이유가 없었다.
`Evidence`가 발화별 증거를 누적하고, 새 발화만 채점한다.

| | 발화 30건 시점 |
|---|---|
| 구 매처 · 전체 재채점 | 60.7초 |
| 신 매처 · 전체 재채점 | 2.14초 |
| **신 매처 · 증거 누적** | **0.023초** |

60번째 발화도 첫 발화와 같은 비용(평균 22.8 ms)이다.
`test_incremental_matches_full_rescore`가 두 경로의 결과가 같은지 검증한다 —
같지 않으면 최적화가 아니라 버그다.

### 남은 미탐 2건은 알고리즘이 아니라 DB 공백이다

`--gaps`가 둘을 구분한다. 미탐 시나리오에서 **어느 단계가 비었는지**만 알린다.

```
[F-C-01] 대출빙자 — 저금리 전환 미끼  → 미탐 (0.531)
   기대 경로 C · 잡힌 단계 ['S6', 'S8']
   **비어 있는 단계: S5**
```

**표현을 제안하지는 않는다.** D08 §07이 요구한 대로 DB를 채우는 사람은
평가 시나리오를 보지 않아야 한다. 평가 시나리오를 쓴 사람이 그걸 보고 키워드를 넣으면
자기가 낸 문제를 자기가 채점하는 셈이 된다.
지금 상태에서 탐지율 80%를 90%로 올리는 것은 쉽지만, 그 수치는 아무 의미가 없다.

### 종단 검증 — 오디오부터 개입까지 실제로 돌려봤다

`eval_mode1.py`가 재는 것은 **텍스트 단계**다. 시나리오 문장을 스코어러에 직접 넣는다.

오디오 → [VAD 분할] → [Whisper 전사] → 채점 → 개입

탐지율 81%는 **전사가 완벽하다고 가정한** 값이다. `e2e_test.py`가 시나리오를 소리로 만들어
WebSocket 서버에 흘려보내고, 서버가 실제로 무엇을 전사하고 어떻게 판정하는지 받아 적는다.

```bash
python ws_server.py --port 8765      # 다른 터미널
python e2e_test.py --all
```

| 시나리오 | 전사 | 최고 위험도 | 개입 |
|---|---|---|---|
| R-A-01 실제 사기 (검사 사칭) | 12개 | 0.750 | **예** |
| R-B-01 실제 사기 (자녀 사칭) | 5개 | 0.750 | **예** |

**전 경로가 이어져 있고 판정도 맞다.** 그런데 텍스트 단계에서는 안 보이던 것이 셋 나왔다.

**① 유령 매칭이 남아 있었다 — 이게 가장 중요하다.**
실제 전사에서 `계좌이체`가 **"계좌에 있는 돈을"**에 매칭됐다(거리 2).
"계좌에"는 완전히 정상적인 한국어인데 텍스트 시나리오에는 없던 형태였다.
4음절은 자모가 8개라 거리 2를 허용하면 **4분의 1이 달라도 통과**한다.
6음절 미만은 거리 1로 조였다(`BUDGET2_MIN_SYLLABLES`).

조인 뒤 탐지율이 81.0% → 76.2%로 떨어졌는데, **잃은 탐지가 전부 유령 매칭 덕이었다.**

| 시나리오 | 매칭되던 것 | 실제 원문 |
|---|---|---|
| R-C-01 | `현금으로 찾` | "현금으로 **상환**하여야" |
| F-C-01 | `지금 바로` | "지금 **불러드리는**" |

의미가 전혀 다르다. 유령 매칭으로 잡히던 것은 실력이 아니라 운이다.
대신 진짜 공백이 드러나 대법원 인용문("기존 대출금을 현금으로 상환하여야 한다")을
근거로 1항을 추가했고 81.0%로 돌아왔다 — 이번에는 실제 근거로.

**② 개입 문구의 조사가 틀렸다.**
`“발설하면” 라는 말이 나왔습니다` — 받침이 있으므로 "이라는"이 맞다.
화면에도 뜨고 음성으로도 읽히는 문장이다. 개입은 피해자를 각성시키는 것이 목적인데
문장이 어설프면 신뢰를 잃는다. 음성 뱅크도 조사별로 조각을 두 개 갖도록 고쳤다 —
하나만 만들어 두면 나머지 경우에 무음이 된다.

**③ VAD가 발화를 기대보다 잘게 자른다.** 8개 발화가 12개로 전사됐다.
지금은 탐지에 영향이 없었지만, 키워드가 분할 경계에 걸리면 매칭이 안 된다.
회피 시나리오 F-E-05(짧은 발화로 쪼개기)가 이미 지연탐지로 그 위험을 계측하고 있다.

**한계** — 합성 음성(Windows SAPI)이라 실제 통화보다 깨끗하다. 잡음도 없고 발음도 또박또박하다.
여기서 나온 전사 정확도는 **상한**이다. `--telephone`으로 통화 채널을 통과시킬 수 있다.

### 실제 공개 녹취로 교차검증 — 자체 시나리오는 성능을 과대평가했다

D08 §07이 요구한 "DB 작성자와 평가 작성자 분리"를 `scenarios.json`은 완전히 만족하지 못한다.
`eval/scenarios_real.json`은 그 문제를 **사기 발화를 한 줄도 짓지 않는 것**으로 우회한다 —
전부 언론·판결·기관이 공개한 인용문이고, 발화 단위로 출처를 붙였다.
연결구에는 위험 키워드를 넣지 않았다. 넣으면 "내가 넣은 것을 내가 찾는" 순환이 된다.

| | 자체 작성 시나리오 | **실제 공개 녹취** |
|---|---|---|
| 탐지율 | 81.2% | **60.0%** |

**자체 시나리오가 성능을 20%p 과대평가하고 있었다.** 이유가 구체적이다.
자체 시나리오 F-A-04는 SBS 녹취를 인용하면서 연결구에
"선생님 명의가 **대포통장**에 도용되어", "**안전계좌**로 자금을 옮기는 절차부터"를 넣었다.
DB가 아는 단어를 내가 넣은 것이다. **인용문만 남긴 순수 버전(R-A-02)은 0.117 "안전"으로
완전히 놓친다.** 시나리오를 직접 쓰면 자기도 모르게 정답을 흘린다.

#### 미탐 2건이 전부 현재 주류 수법이었다

| 실제 발화 | 왜 못 잡았나 |
|---|---|
| "**조용한 공간**을, **독립적인 공간으로 가셔서** 통화 안 되십니까?" | S4에 **물리적** 고립 유도가 없었다 — 정보 고립(말하지 마)만 있었다 |
| "대출을 받아 금감원 **직원에게 전달**하십시오" | S5가 `만나서/직접/현금 전달`뿐이라 `~에게 전달` 형태를 놓쳤다 |
| "계좌에 있는 돈을 안전하게 관리하기 위해 **자산 보호 신청**을 해야 합니다" | '안전계좌'가 아니다. 실제 사건은 다른 말을 쓴다 |

**대면편취형(현금 인출 후 직접 전달)이 전체 보이스피싱의 66.9%다.**
계좌이체형은 지연인출제도 이후 줄었다. DB가 이체 중심이면 **주류 수법을 놓친다.**
출처를 붙여 5항(S4 3 · S5 2)을 추가했고 탐지율이 **60% → 80%**가 됐다.

> **오염 경고** — 이 세트가 찾은 공백을 이 세트를 보고 채웠으므로,
> 추가 후의 80%는 상한이다. 진짜 성능을 확인하려면 **아직 쓰지 않은 공개 녹취**가 더 필요하다.
> 정상(family) 쪽은 DB 변경의 영향을 받지 않았고 추가 전후 모두 오탐 0건이라 오염이 없다.

#### 가족 금융 대화는 전부 통과했다

오탐이 실사용을 막는 가장 큰 요인이라 이쪽이 세트의 절반이다.
등록금·병원비·전세 계약금·경조사비·대출 갈아타기·상속 — **12건 전부 "안전"**.

이 대화들에는 `계좌`·`이체`·`송금`·`급하게`·`오늘 중으로`가 정당하게 나온다.
FAM-11(형제에게 진짜로 돈을 빌리는 통화)은 지인 사칭 사기와 표면 구조가 거의 같은데도
0.000이다. 인용 판정과 경로별 정규화가 함께 작동한 결과다.

전체(자체 + 회피 + 실제) **57건 기준 오탐률 0.0% [0.0, 9.6]** —
정상 시나리오가 36건으로 늘면서 신뢰구간이 13.8% → 9.6%로 좁아졌다.

### 회피 평가 — 우리가 넣은 규칙을 우리가 공격했다

**억제 장치는 전부 양날이다.** 정상 통화를 살리려고 넣은 규칙이 사기범에게는
빠져나갈 구멍이 된다. 규칙을 넣은 사람이 직접 공격해봐야 한다.
`eval/scenarios_evasion.json`이 그 세트다 — 전부 label이 fraud이며 **반드시 잡혀야 한다.**

위협 모델은 "사기범이 미리내의 판정 규칙을 안다"이다. 과한 가정이 아니다 —
조직적 보이스피싱은 대본을 계속 고치고 통신사 탐지를 우회한 전례가 있다.

**그리고 실제로 뚫렸다.**

```
[F-E-02] 회피② 예방 문구를 도배해 감점을 쌓는다  →  미탐
  최종 0.000 (안전)
  critical 발동: C1, C2      ← 하한 0.75가 걸려야 하는 상태
  pair 발동: P1
  benign 감점: 보이스피싱 조심, 절대 알려주지 마, 112에 신고, 1332,
              본인 확인 절차, 천천히 생각      ← 감점 0.90
```

C1·C2·P1이 **모두 발동한 통화가 0.000 "안전"으로 나왔다.**
원인은 바로 위에서 우리가 고친 것이었다 — 예방 교육 오탐을 막으려고 하한을
`CRITICAL_FLOOR - penalty`로 두었더니, 예방 문구를 여섯 개 흘리는 것만으로
하한이 통째로 지워졌다. **정상 통화를 살리려던 규칙이 그대로 회피 도구가 됐다.**

가정이 아니다. SBS가 공개한 실제 녹취에서 사기범이 예방 문구를 말한다 —
"주민등록번호, 계좌번호, 통장 비밀번호 절대로 말씀하시면 안 되시고".
benign 목록의 '본인 확인 절차'·'112에 신고'·'1332'·'영업점 방문'은
전부 사기범 화법에 흔한 말이다.

**고친 방법** — 하한은 감점을 받지 않는다. 감점으로 무너뜨릴 수 있으면 하한이 아니다.
원래 막으려던 예방 교육 대화는 **인용 판정이 이미 처리하고 있었다** —
그런 대화에서는 위험 표현이 전부 인용문이라 critical이 아예 발동하지 않는다.
같은 문제를 두 군데서 풀려다 구멍을 낸 것이었다.
여기에 감점 총량 상한(`BENIGN_PENALTY_MAX`)을 더했다.

| | 이전 | 이후 |
|---|---|---|
| 회피 성공률 | 33.3% | **16.7%** |
| 오탐률 | 0.0% | 0.0% |
| 탐지율 | 75.0% | 81.2% |

남은 회피 1건(F-E-04)은 **키워드를 우회 표현으로 바꾸는 것**이다 —
"안전계좌" 대신 "국고 보호 예치 계좌", "체포영장" 대신 "신병 확보 절차".
이건 알고리즘 결함이 아니라 **사전 기반 탐지 방식의 한계**다.
DB를 늘려도 표현은 무한히 만들 수 있다. 상용 서비스가 패턴 위에 학습 모델을
얹는 이유가 이것이다. 고칠 수 있는 척하지 않고 한계로 기록한다.

### STT 오차 견고성 — 깨끗한 전사에서만 성립하는 수치였다

평가 시나리오는 전부 깨끗한 텍스트인데 **실제 입력은 Whisper 출력**이다.
게다가 오탐을 줄이려고 근사매칭을 **더 엄격하게** 바꿨으므로
(4음절 미만 차단·초성 일치 요구), 정밀도를 얻는 대신 견고성을 잃었을 가능성을
반드시 확인해야 했다.

`eval/stt_noise.py`가 한국어 STT에서 실제로 흔한 오차만 넣는다 —
중성 혼동(ㅐ↔ㅔ, ㅚ↔ㅙ), 종성 탈락, 초성 경음 혼동, 띄어쓰기.

```bash
python eval_mode1.py --noise-curve --repeat 12
```

```
   오차율 │        근사매칭 켬        │  근사매칭 끔 (정확 일치만)
       │   탐지율   오탐률     F1  │   탐지율   오탐률     F1
    0%  │   81.2%    0.0%   89.7% │   81.2%    0.0%   89.7%
    5%  │   76.0%    5.2%   82.8% │   72.9%    3.5%   81.9%
   10%  │   70.8%    3.8%   80.1% │   61.5%    2.8%   74.0%
   20%  │   67.2%    6.9%   75.7% │   48.4%    3.8%   62.4%
   25%  │   65.6%   10.8%   72.1% │   45.8%    6.2%   58.9%
```

**두 가지가 드러났다.**

**① 근사매칭은 값을 한다.** 오차 25%에서 탐지율 65.6% 대 45.8% — 19.8%p 차이다.
엄격하게 조인 뒤에도 근사매칭의 효용은 남아 있다.

**② "오탐률 0%"는 깨끗한 전사에서만 성립한다.** 오차가 끼면 4~11%로 오른다.
근사매칭이 망가진 정상 텍스트에 걸리기 때문이다.
**발표에서 0%만 말하면 거짓말이 된다.**

여기에 대응해 두 가지를 넣었다. 둘 다 원리가 같다 —
**판정 결과가 무거운 신호일수록 더 엄격한 증거를 요구한다.**

여기에 대응해 `CRITICAL_MAX_EDIT`를 넣었다. 원리는 이렇다 —
**판정 결과가 무거운 신호일수록 더 엄격한 증거를 요구한다.**
C1~C5는 하나만 걸려도 위험도를 0.75로 밀어올리므로, 일반 단계 키워드와 같은
허용치를 쓸 이유가 없다. 편집거리 1로 조였더니 오차 25%에서 오탐률
17.8% → 13.9%, **탐지율 손실은 없었다.**

같은 착상을 단계 점수 쪽에도 적용해 봤다가 **뺐다.** 편집거리별 가중치를
점수에 곱하는 방식이었는데, 오차 5·10·15·20·25% 다섯 구간 전부
결과가 **소수점까지 같았다.**
위험 판정은 critical·pair가 만드는 **이진 하한**이 지배하는데 가중치는 등급 점수
경로에만 걸리기 때문이다. 하한에는 증거의 세기를 반영할 자리가 없다.
측정해서 효과가 없는 코드는 남기지 않았다 — 근거는 `scorer.py`에 주석으로 남겼다.

### 이 수치를 어떻게 읽어야 하나 — 신뢰구간을 함께 찍는다

**오탐률 0%를 "오탐이 없다"로 읽으면 안 된다.** 그래서 주의 문장 대신
평가 출력에 **Wilson 95% 신뢰구간**을 넣었다. 읽는 사람이 caveat을 건너뛰어도 보인다.

```
                          값      95% 신뢰구간
  탐지율 (recall)     81.2%   [57.0, 93.4]
  정밀도 (precision) 100.0%   [77.2, 100.0]
  오탐률 (위험)        0.0%   [0.0, 13.8]
```

**정상 24건에서 오탐 0건이어도 실제 오탐률은 13.8%까지 가능하다.**
Wald(정규근사)는 0%에서 폭이 0이 되어 이 사실을 감춘다. 그래서 Wilson을 쓴다.
`mirinae.metrics.wilson_ci`를 그대로 재사용한다 — 두 군데서 다르게 계산하면
보고서마다 숫자가 달라진다.

그리고 위에서 봤듯 **전사에 오차가 끼면 점 추정 자체가 오른다.**

평가 세트의 한계는 `eval/scenarios.json`의 `authoring_note`에 적어 두었다 —
작성자가 pattern_db의 benign·critical 목록을 이미 본 상태였으므로
**완전히 독립적인 평가가 아니며 상한으로 읽어야 한다.**

정직하게 말하면 이렇다.

> 깨끗한 전사·시나리오 40건 기준으로 탐지율 81.2%, 오탐률 0%다.
> 전사 오차 10%에서는 탐지율 73.3%, 오탐률 5.0%로 내려간다.
> 탐지 규칙을 아는 상대에게는 6건 중 1건을 놓친다.
> 시나리오가 40건이므로 이 수치들의 신뢰구간은 넓다.

## 한국어 어절 분리 매칭 — 가장 큰 구조적 결함이었다

탐지율이 81%에서 멈춰 있던 진짜 이유다. 놓친 시나리오 4건을 발화 단위로
뜯어보니 원인이 하나로 모였다 — **한국어는 어절 사이에 조사·부사가
자유롭게 끼어드는데, 연속 문자열 매칭은 그걸 구조적으로 못 잡는다.**

```
키워드              실제 발화                              결과
─────────────────────────────────────────────────────────────
가족에게 알리지      "가족에게 이 사실을 알리지 마세요"       놓침
기존 대출 상환       "기존 대출을 먼저 상환하셔야"            놓침
국고 계좌           "국고 보호 예치 계좌로"                  놓침
수사 협조           "수사에 적극 협조해 주셔야"              놓침
```

셋 다 사기범이 노려서 쓴 회피가 아니다. **그냥 말하면 이렇게 된다.**
놓치는 쪽이 기본값이었다는 뜻이다.

자모 근사매칭으로는 풀 수 없다. 끼어든 "을 먼저 "가 자모 7개라
편집거리 예산(최대 2)을 훨씬 넘는다. 예산을 늘리면 오탐이 폭발한다.

그래서 **어절 단위로 쪼개 순서대로 찾는** 경로를 따로 뒀다
(`Matcher.find_gapped`). 각 어절은 기존 매칭을 그대로 쓰고,
어절 사이에 몇 음절까지 끼어들 수 있는지만 상한을 둔다.

### 상한은 스윕으로 정했다

| 간격 | 탐지율 | 오탐률(위험) | 회피 성공률 |
|---:|---:|---:|---:|
| 끔 | 81.0% | 0.0% | 16.7% |
| 0~3 | 81.0% | 0.0% | 16.7% |
| **4** | **85.7%** | **0.0%** | **0.0%** |
| 5~12 | 85.7% | 0.0% | 0.0% |

4에서 이득이 나타나고 그 위로는 같다. **회피 여지가 가장 작은 4**를 택했다
(`QUOTE_WINDOW`를 고를 때와 같은 원칙이다). 오탐률이 전 구간 0%라고 해서
12가 안전하다는 뜻은 아니다 — 정상 통화 36건에서 증거가 안 나왔을 뿐이다.

> **스윕이 한 번 헛돌았다.** 처음 표는 간격 0부터 12까지 전부 같은 값이
> 나왔다. 기본 인자 `max_gap: int = GAP_MAX_SYLLABLES`가 함수 정의 시점에
> 묶여서, 모듈 전역을 바꿔도 반영되지 않았다. **아무것도 스윕하지 않는
> 스윕이었다.** 하마터면 그 표를 보고 값을 골랐을 것이다.

오탐 방지 제약 셋을 걸었다.
- **연속 매칭이 실패했을 때만** 시도한다. 기존 판정을 바꾸지 않는다.
- 3음절 미만 어절은 **정확 일치만** 인정한다. 짧은 어절에 근사까지 허용하면
  아무 데나 걸린다.
- 문장 단위로 호출되므로 문장을 넘어가지 않는다.

발화당 비용은 6 ms 늘었다(62.6 → 68.6 ms). 처음엔 40 ms였는데,
짧은 어절이 문자열에 아예 없으면 순서 탐색을 시작하지 않도록 조기 종료를
넣어 걷어냈다.

## 완곡 표현 — 사기범은 키워드를 피해서 말한다

gapped 매칭으로 잡히지 않은 나머지는 표현 자체가 DB에 없었다.

```
"제가 지금 불러드리는 계좌로 입금해 주시면"      ← "안전계좌"를 피했다
"지금 알려드리는 곳으로 옮겨 두시면 됩니다"      ← "계좌"라는 말도 피했다
"국고 보호 예치 계좌로 자금을 이관하셔야"        ← 행정용어로 위장했다
"금일 중으로 처리하셔야"                        ← "오늘"의 한자어
```

11항을 더했다. 그런데 여기서 문제가 생긴다 — "알려드리는 계좌"를 넣으면
정상 기관의 "계좌번호 알려주시면"도 걸리지 않나?

**한국어 경어법이 방향을 구분해 준다.**

```
사기   "제가 알려드리는 계좌로 보내세요"    겸양 '-드리는' → 화자가 계좌를 준다
정상   "계좌번호 알려주시면 입금해 드릴게요"  존경 '-주시면'  → 청자가 계좌를 준다
```

방향이 정반대다. 정상 통화(B-13·B-14·FAM-05·H-B-04)는 **전부** 후자였다.
문법이 판별해 주므로 표현 목록을 늘려도 오탐이 늘지 않는다.

## P4 — 사칭 없이도 성립하는 사기의 본질

기존 조합 신호 P1~P3은 전부 "누구를 사칭하는가"로 나뉜다(기관·대출·가족).
그래서 사기범이 사칭 단계만 피하면 경로가 잡히지 않고 점수가 오르지 않았다.
실제 녹취 기반 R-A-02가 그렇게 빠져나갔다.

**고립(S4) + 자금이동(S5)** 은 사칭 없이도 성립한다. 그리고 정상적인 금융
거래가 이 둘을 동시에 요구할 이유가 없다 — 정상 표지 목록에 "가족과 상의"가
들어 있는 것이 그 방증이다.

측정: 이 조합은 사기 12건에서 발동하고 정상 36건에서 0건이었다.
그래서 넣었고, 탐지율이 100%가 됐다.

### 그 100%는 과적합이었다

**그 규칙들은 그 시나리오들을 보면서 만들었다. 훈련셋 성적이다.**
그대로 발표하면 과적합을 성능으로 파는 것이 된다.

그래서 새 규칙 각각을 **깨뜨리려고** 만든 검증셋을 따로 썼다
(`eval/scenarios_holdout.json`). 정상 7건은 새 규칙을 잘못 발동시키러,
사기 6건은 새 규칙을 피해 가려고 설계했다.

첫 실행 결과다.

```
탐지율   100.0%
오탐률    42.9%   ← 정상 7건 중 3건을 위험으로 판정
```

셋 중 하나가 **은행 창구 직원이 보이스피싱을 말리는 통화**였다.
막아야 할 쪽을 사기로 본 것이다. 최악의 오탐이다.

### 원인은 깨끗하게 갈렸다

| | S4 근거 | S5 근거 | 판정 |
|---|---|---|---|
| 정상 H-B-01 | 조용한 곳 | **이체** | 오탐 |
| 정상 H-B-02 | 대외비 | **이체** | 오탐 |
| 정상 H-B-03 | 한테는 말하지 | **송금** | 오탐 |
| 사기 H-F-04 | 수사 기밀 | 현금으로 찾 · 수사관에게 전달 | 정탐 |
| 사기 H-F-05 | 한테는 말하지 | 알려드리는 계좌 | 정탐 |
| 사기 H-F-06 | 수사 기밀 | 안내해드리는 계좌 · 예치하시면 | 정탐 |

오탐 3건은 전부 **"이체"·"송금" 단독**이고, 정탐 3건은 전부 구체적 형태다.

**돈을 보낸다는 사실 자체는 사기의 증거가 아니다.** 증거는 어디로·어떻게
보내느냐다 — 화자가 즉석에서 지정한 계좌, 현금 인출 후 대면 전달, 인증정보 요구.

그래서 키워드에 `generic` 표시를 넣었다. generic 표현은 단계 점수에는 그대로
들어가되, 하한 0.75를 강제하는 조합 신호를 **혼자서는 성립시키지 못한다**
(`Pair.needs_specific`). P4의 오탐률이 42.9% → 0%가 됐다.

### 사기범은 계좌 주인을 밝힐 수 없다

P4 게이트를 걸자 F-B-03(지인 사칭)이 다시 빠졌다. "송금"만 걸렸기 때문이다.
그런데 정상 통화를 다시 보니 전부 계좌의 **귀속을 밝히고** 있었다.

```
정상   "내 계좌로"(B-15·FAM-01·H-B-07) · "여행사 계좌로"(H-B-03)
       "집주인 명의 계좌로"(B-13) · "법무법인 에스크로 계좌로"(H-B-02)
사기   "이 계좌로"(F-B-03) · "지금 불러드리는 계좌로"
```

대포통장이라 주인을 말할 수 없다. **구조적 제약이라 회피하기 어렵다.**
`이 계좌로` 계열을 구체 표현으로 넣어 F-B-03을 되찾았다.

## 모드 1 최종 성적

```
                       훈련셋(57건)      검증셋(13건)
탐지율                  100.0%            100.0%
정밀도                  100.0%            100.0%
오탐률(위험)              0.0%              0.0%
회피 성공률                0.0%                —
```

**두 숫자를 같은 무게로 읽으면 안 된다.** 검증셋은 규칙을 만든 뒤에 썼지만,
그 결과를 보고 P4 게이트와 `이 계좌로`를 다시 고쳤다. **그 시점에서
검증셋도 훈련셋이 됐다.** 다음에 성능을 주장하려면 새 검증셋이 필요하다.

표본도 작다. 검증셋 13건에서 오탐률 0%의 95% 신뢰구간은 [0.0, 35.4]다 —
"오탐이 없다"가 아니라 **"오탐률이 35%보다 낮다"** 까지가 이 데이터로
말할 수 있는 전부다.

### 두 번째 검증셋 — 첫 검증셋 이후에 만든 규칙을 공격했다

첫 검증셋은 결과를 보고 규칙을 고쳤으므로 이미 훈련셋이다. 다시 돌려 0%가
나오는 건 당연하다. 그래서 **generic 게이트·`이 계좌로`·경어법 방향**을
직접 공격하는 두 번째 셋을 새로 썼다(`eval/scenarios_holdout2.json`,
사기 10 · 정상 10). 첫 실행 결과다.

```
탐지율   80.0%
오탐률   20.0%   ← 정상 10건 중 2건을 위험으로 판정
```

**튜닝한 세트의 100%/0%와 전혀 다른 숫자다.** 그리고 둘 다 출시됐을 버그였다.

**K-B-09 국세청 환급 안내 → 위험 0.750**

> "저희는 계좌번호나 비밀번호를 전화로 **묻지 않습니다**"

`비밀번호`가 걸리고 기관명(S1)과 만나 P1이 발동했다.
이건 **모든 정상 금융기관·공공기관이 쓰는 표준 안내 문구**다.
실사용에서 계속 터졌을 것이다. 인용과 같은 구조라 같은 자리에서 처리했다 —
화자가 그 행위를 **하지 않는다고 선언**하는 문장이므로 지시가 아니다
(`context.py`의 `DISCLAIMER_MARKERS`).

사기범이 이 문구를 흉내내면? 그 문장 하나가 무효가 될 뿐이다.
사기는 결국 요구를 해야 하고 그 문장은 따로 걸린다 — 예방 문구를 도배하는
회피(F-E-02·F-A-04)가 이미 그렇게 잡힌다.

**K-B-08 이직 협상 → 위험 0.750**

> "사이닝 보너스는 급**여 계좌로** 이체됩니다"

바로 앞 절에서 자랑스럽게 넣은 `이 계좌로`가 원인이다.
"여계좌로"와 자모 거리 1, 초성도 `ㅇㄱㅈㄹ`로 같다. **4음절짜리 패턴을
근사매칭에 열어둔 것이 잘못**이었다. 키워드 단위로 근사를 끄는
`exact_only`를 넣어 막았다.

DB 공백도 둘 나왔다 — 메신저피싱의 신분증·카드 사진 요구, 릴레이 사기
1단계의 "끊지 마시고". 둘 다 실제 수법인데 비어 있었다.

고친 뒤 다시 돌린 결과다.

| | 훈련셋(57) | 검증셋1(13) | 검증셋2(20) |
|---|---:|---:|---:|
| 탐지율 | 100.0% | 100.0% | 90.0% |
| 정밀도 | 100.0% | 100.0% | 100.0% |
| 오탐률 | 0.0% | 0.0% | 0.0% (20.0%에서) |

검증셋2에 남은 1건(K-F-06)은 릴레이 사기의 1단계만 담은 시나리오로,
`expect`를 "주의"로 써둔 것이다. 0.262(안전) → 0.453(**주의**)로 올라
의도대로 동작했지만, 평가 하네스가 "위험"만 탐지로 세기 때문에 미탐으로
표시된다. **탐지 실패가 아니라 라벨과 집계 기준의 불일치다.**

> **그리고 검증셋2도 이제 훈련셋이다.** 결과를 보고 규칙을 고쳤기 때문이다.
> 위 표의 세 번째 열을 "검증 성적"으로 인용하면 안 된다.
> 정직하게 인용할 수 있는 숫자는 **처음 돌렸을 때의 80.0% / 20.0%** 뿐이다.
>
> 이 패턴이 두 번 반복됐다는 사실 자체가 결론이다 —
> **새 검증셋을 만들 때마다 실제 결함이 나왔다.** 세 번째를 만들면
> 또 나올 가능성이 높다고 보는 편이 맞다.

### 세 번째 검증셋 — 지금까지 중 가장 나빴고 가장 값졌다

2차 직후에 넣은 규칙 중 하나(고지 문구 억제)는 **새 회피 표면**이다.
억제는 정의상 "점수를 지우는" 장치라, 사기범이 그걸 켤 수 있으면 끝난다.
그래서 그것을 정면으로 공격하는 세 번째 셋을 썼다
(`eval/scenarios_holdout3.json`, 사기 11 · 정상 11).

파일에 **예측을 미리 적어 두었다** — "고지 문구 공격은 뚫릴 것으로 예상한다".

```
탐지율   54.5%
오탐률   18.2%
경로판정 45.5%
```

**예측은 틀렸다.** 고지 문구 공격(T-F-01·02)은 둘 다 잡혔다(0.750·0.794).
억제가 문장 단위라 다른 문장의 지시가 그대로 남았다. 예측을 적어 둔 덕에
"맞혔다"고 기억을 고쳐 쓸 수 없었다.

대신 예상하지 못한 곳이 무너졌다.

**오탐 — 사기를 막으려는 쪽을 사기로 봤다**

| | 내용 | 점수 |
|---|---|---|
| T-B-02 | 은행 ARS의 보이스피싱 **경고 안내** | 0.750 |
| T-B-11 | 노인복지관 강의에서 수법을 **실연** | 0.750 |

둘 다 수법을 그대로 말하는데 **인용 어미가 없다.** 3인칭 서술("~하는 전화가
있습니다")과 역할 연기라서다. 인용 판정이 통째로 비켜 갔고 C1·C5가 발동했다.

서술 표지를 억제 계열에 추가했다(`DESCRIPTIVE_MARKERS`). 표지를 좁게 잡은
이유가 있다 — "요즘 사기가 많으니 안전계좌로 옮기세요"처럼 '사기'라는 단어만
흘려도 억제가 켜지면 그 자체가 회피로다. 그래서 **서술 서술어 형태**만
인정한다(사칭해·사기입니다·수법입니다). 사기범은 자기 지시를 두고
"이것은 사기입니다"라고 말하지 않는다. 테스트로 고정해 두었다.

**미탐 — DB에 통째로 빠진 유형들**

| | 유형 | 원인 |
|---|---|---|
| T-F-07 | **은행 사칭** | S1에 은행·카드사가 아예 없었다. 검찰·금감원·경찰·국세청뿐 |
| T-F-06 | 몸캠피싱 협박 | 금융 용어가 하나도 없는 유형 |
| T-F-05 | 납치 협박 | "말하지 마라" 대신 결과를 예고한다 |
| T-F-08 | 중고거래 안전결제 | 사칭 대상이 없어 P1~P3이 못 잡는다 |
| T-F-03 | "이 개좌로" | 2차에서 `exact_only`로 바꾸자 STT 변형을 놓쳤다 |

은행 사칭이 비어 있던 것이 가장 뼈아프다. 흔한 유형인데
**세 번째 검증셋을 만들기 전까지 아무도 몰랐다.**

C6(문자 링크 앱 설치)를 단독 고위험으로 새로 넣었다. 원격제어(C5)와 같은
계열이고 결과도 같다 — 기기 장악. 정상 거래는 공식 스토어를 안내하지
스스로 보낸 링크를 누르게 하지 않는다.

그리고 C6를 넣자 **기존 테스트 하나가 바로 깨졌다** — 대응 문구가 없어
경고가 무음이 될 뻔했다. 통화 중에는 화면을 못 보므로 음성이 주 매체인데
하필 그 순간 침묵하는, 조용히 틀리는 종류다.

|---|---:|---:|---:|---:|
| 탐지율 | 100.0% | 100.0% | 90.0% | 90.9% |

스위치를 하나 더 만드는 일이라 하지 않았다. T-F-09(부고 조의금)는

계좌 공유(T-B-06)를 텍스트만으로 가르는 방법을 찾지 못했다.

### 네 번째 검증셋 — 예측을 적고 절반 맞혔다

3차에서 넣은 서술 표지 억제는 고지 문구에 이은 **두 번째 회피 표면**이다.
그리고 3차에서 넣은 표현 중 "찍어서 보내"·"신고하면"·C6(링크 앱)는
정상 업무에서 매우 흔한 말인데 아직 오탐을 재보지 않았다.
그 둘을 표적으로 네 번째 셋을 썼다(사기 10 · 정상 11).

예측을 파일에 미리 적었다 — "찍어서 보내와 C6에서 오탐이 나올 것으로
예상한다. 서술 표지 공격은 문장 단위라 막힐 것으로 본다."

```
탐지율   80.0%
오탐률   18.2%
경로판정 50.0%
```

**절반 맞았다.** 서술 표지 공격은 예상대로 막혔다(Q-F-01 0.794 · Q-F-02 0.750).
C6 오탐도 예상대로 나왔다. 다만 "찍어서 보내"는 예상과 달리 오탐이 0건이었다 —
부동산·병원·법인카드 정산 셋 다 통과했다.

**오탐 2건 — 둘 다 C6가 너무 넓었다**

| | 걸린 문장 | |
|---|---|---|
| Q-B-06 | "문자로 보내드린 링크는 저희가 **보내지 않으니 누르지 마세요**" | 0.750 |
| Q-B-07 | "문자로 보내드린 링크에서 신청서 작성하시면 됩니다" | 0.750 |

Q-B-06은 링크를 **누르지 말라는 경고**였다. 그걸 위험으로 판정했다.
`문자로 보내드린 링크`를 단독 고위험 변형에 넣은 것이 잘못이었다 —
정상 기업이 일상적으로 쓰는 말이다. **위험한 것은 링크가 아니라
링크로 앱을 설치하는 것**이다. 링크 단독 표현은 S5 단계 점수로만 남겼다.

C6는 3차에서 내가 넣은 것이다. **한 검증셋이 만든 규칙을 다음 검증셋이
깎아냈다.**

**미탐 2건 — 또 한국어 형태가 빠져 있었다**

> "부모님**께는 알리지** 마세요"

S4의 고립 표현은 전부 "말하지"만 있고 **"알리지"가 없었으며, 높임 조사
"께"도 빠져 있었다**(Q-F-08). 완전히 자연스러운 한국어인데 통째로 비어 있었다.
gapped 매칭 때와 같은 종류의 결함이다 — 사기범의 회피가 아니라 그냥 말하면
이렇게 된다.

Q-F-05(자영업자 노쇼 사기)는 사칭도 고립도 없이 "대신 결제해 달라"로만 간다.
S8에 선결제·대리결제 요구를 넣어 P2가 성립하게 했다.

### 다섯 번째 검증셋 — 예측이 둘 다 틀렸다

형태 규칙을 표적으로 다섯 번째 셋을 썼다(사기 12 · 정상 12).
예측을 두 개 적어 두었다.

> "함구 규칙에서 오탐이 나올 것으로 예상한다. 특히 P-B-01(의사가 보호자에게)과
> P-B-03(교사가 부모에게)이 위험하다. 미탐은 어간 밖 표현(함구하다·쉬쉬하다)에서
> 나올 것으로 본다."

```
탐지율   75.0%
오탐률   16.7%
경로판정 58.3%
```

**둘 다 틀렸다.** 의사·부모·교사·인사팀의 정당한 함구 요구는 전부 통과했고
(0.10~0.13), 어간 밖 표현 공격(P-F-01·02·03)도 전부 잡혔다.

이유가 있다. 함구 요구만으로는 점수가 오르지 않고, generic 게이트가 P4를
막는다 — S4는 걸리되 자금이동이 구체적이지 않으면 위험이 되지 않는다.
반대로 사기 쪽은 어간을 피해도 다른 신호(기관 사칭·안전계좌)가 남아 있었다.
**어느 한 축만 피해서는 빠져나가지 못한다는 뜻이다.**

실제 실패는 다른 곳이었다.

### 고치다가 낸 회귀 — 두 번 되돌렸다

지자체 사칭(P-F-12)을 잡으려고 `구청·시청·주민센터`를 S1에 넣었더니
**검증셋 1차가 깨졌다**(오탐 0 → 14.3%). 걸린 문장이 이것이다.

> "본인 확인이 필요하니 가까운 **주민센터 방문**하셔도 됩니다"

정상 안내다. 기관을 **언급**하는 것과 **사칭**하는 것은 다른데 구분하지 않았다.

첫 시도는 P4에만 걸어 둔 generic 게이트를 P1~P3에도 거는 것이었다.
관공서 오탐은 사라졌지만 **회피 시나리오 2건을 잃었다**(회피 성공률 0 → 33%).
되돌렸다. 요구할 증거의 양이 쌍마다 다르기 때문이다 —
P4는 사칭 단계가 없어 증거가 S4+S5뿐이라 게이트가 필요하고,
P1~P3은 사칭 단계라는 독립 증거가 이미 있다.

결국 진짜 원인을 고쳤다. 지자체 기관명을 S1에서 뺐다.
P-F-12는 S1 없이도 P4(고립+자금이동)로 잡힌다 —
**사칭 단계 없이 성립하는 쌍을 둔 이유가 정확히 이것이었다.**

### 여섯 번째 검증셋 — 처음으로 예측이 맞았고, 처음으로 오탐이 0이었다

5차에서 구어체 인용 어미를 넓히며 `래서`를 넣었다. 그런데 접속부사
**"그래서"에 `래서`가 그대로 들어 있다.** 억제 목록에 흔한 말이 섞이면
그 자체가 회피로다. 그것과, 여태 한 번도 흔들지 않은 **통화 구조**를
표적으로 여섯 번째 셋을 썼다(사기 12 · 정상 12).

```
탐지율   75.0%
정밀도  100.0%
오탐률    0.0%   ← 여섯 번 중 처음
```

예측은 두 개였다. 둘 다 맞았다.

**① "'래서' 구멍은 뚫릴 것으로 예상한다"** — 뚫렸다.

> "안전계좌로 이체하셔야 합니다 **그래서** 지금 바로 진행하겠습니다"
> → 0.593 주의
>
> "국고 계좌 **그래서** 그쪽으로 잔액을 옮겨 두십시오"
> → 0.437 안전

지시 뒤에 접속부사 하나만 붙이면 억제가 켜졌다. `래서`를 뺐다.

> **억제를 늘릴 때마다 그 표지가 정상 문장에 우연히 들어갈 확률을 먼저 봐야 한다.**
> 세 번째 겪는 일이다 — 2차 기관 고지, 3차 서술 표지, 6차 '래서'.

자모 `ㄴ`은 결합하지 못한다. 융합형을 따로 적었다.

| 정상 (V-B10) | "제가 **원격제어로** 봐드릴게요 사내 프로그램이요" | 0.750 위험 |

**정확히 반대로 나왔다.** 같은 행위를 사기범이 부드럽게 말하고 정상이
정확한 용어로 말했더니 판정이 뒤집혔다. `원격으로`를 C5에 더하면 미탐은
풀리지만 오탐은 그대로다 — **어휘로는 풀 수 없는 문제**다.

같은 계열로 남은 것들:

- **V-P1-F** — "제가 알려드리는 계좌로 삼백만 원만" (0.117). 사칭도 고립도 없이
  자금 지정만 있다. 짝인 V-P1-B와 0.117 대 0.000으로 **차이는 보되 알리지 못한다.**
- **V-P5-F** — "가시는 동안 통화 끊지 마시고" (0.310). 인출 + 통화 유지는
  대면편취의 전형인데 점수가 오르지 않는다.
- **V-S2** — 잡담 사이에 "인출하신 다음에 직원한테 건네주시면" 한 마디 (0.000).
- **V-B2** — 진짜 가족이 다그치는 통화가 0.525 주의.

**이것들을 지금 고치지 않는다.** 여기서 어휘를 더 넣으면 10차만 좋아지고
다음 셋에서 같은 자리가 다시 터진다 — 아홉 번 반복해서 확인한 패턴이다.
남은 것은 어휘가 아니라 **맥락 판단**의 문제이고, 그건 패턴 매칭 층위에서
풀리지 않는다.

## 맥락 층위 — 명사가 아니라 행위 프레임

10차에서 "어휘로는 풀 수 없다"고 적고 남겨 둔 것들을 프레임 층위로 옮겼다
(`mirinae/mode1/frames.py`).

### 무엇이 문제였나

같은 결함을 이미 세 번 고쳤는데, 셋 다 **명사를 보고 행위를 못 본** 것이었다.

| | 잘못 본 것 | 실제 판별자 | 발견 |
|---|---|---|---|
| C7 통장 | "통장이랑 도장"이라는 명사쌍 | 지참(정상) 대 **전송**(사기) | 9차 |
| C8 계좌 | 계좌를 말한다는 사실 | 공식 경로 안내 대 **차단** | 10차 |
| C5 원격제어 | "원격제어"라는 명사 | 언급 대 **설치 지시** | 10차 |

C5는 **정확히 반대로** 나왔다 — 사기범이 "원격으로"라고만 말해 빠져나가고
(0.000) 사내 IT 지원이 정확한 용어를 써서 걸렸다(0.750).

### 프레임이란

보이스피싱은 결국 한 가지를 시켜야 성립한다 — **피해자의 자산이나 기기
통제권을 사기범이 지정한 곳으로 옮기는 것.** 그 지시는 세 자리로 되어 있다.

```
[무엇을]          [어디로 / 누구에게]        [누가 시키는가]
 자금·통장·기기     화자가 지금 지정하는 곳     화자 → 청자
```

**세 자리가 다 차야 위험하다.** `인출`도 `설치`도 `계좌`도 하나만 보면 일상어다.
단계 점수(S1~S8)는 *무엇이 언급됐는가*를 세고, 프레임은 *그것들이 어떻게
묶였는가*를 본다.

| 프레임 | 구성 | 잡는 것 |
|---|---|---|
| `F-대면편취` | 인출 + 사람 + 건네 | 현금을 찾아 사람에게 넘기라는 지시 |
| `F-불명출처설치` | 출처 불명 대상 + 설치·실행 | "화면에 뜨는 거", "문자로 보내드린 링크" |
| `F-원격권한` | 설치 **지시** + 원격 접근 | 청자에게 시킨 뒤 접근하겠다는 구성 |

`F-대면편취`가 특히 컸다. 인출도 S5, 전달도 S5라 **한 단계에 뭉개져** 조합
신호가 만들어지지 않았다(V-S2에서 0.000). 전체 피해의 66.9%가 이 유형인데
정의 그대로의 문장을 못 잡고 있었다.

프레임도 키워드와 똑같이 문장 단위로 돌고 인용·고지·서술 판정을 통과한다.
그리고 **부정형을 배제한다** — "링크는 **누르지 마세요**"는 경고지 지시가 아니다.

### 결과

```

최소대립쌍 5쌍이 전부 갈렸다. 특히 쌍 1은 **계좌 출처 하나로** 갈린다 —
"제가 지금 알려드리는 계좌로"(위험) 대 "저번에 쓰던 제 계좌로"(안전).

## 열한 번째 — 실사용 조건에서 재기

열 번을 돌려도 근본 한계는 그대로다. **문제와 답을 같은 사람이 쓴다.**
시나리오를 더 어렵게 만들어도 그건 해결되지 않는다. 그래서 11차는 방향을 바꿨다 —
**"실제로 쓰면 무슨 일이 일어나는가"** 를 잰다.

빠져 있던 것이 둘이었다.

### ① 사용자는 통화 **도중**에 경고를 받는다

지금까지 평가는 통화 **최종** 점수만 봤다. 정상 통화가 3번째 마디에서 위험으로
떴다가 마지막에 안전으로 끝나면, 평가는 통과로 세지만 사용자는 이미 경고음을 들었다.

전체 정상 통화 172건을 마디 단위로 다시 쟀다.

```
최종 점수가 '위험'            1건  (0.58%)
통화 도중 '위험'을 지남        1건  (0.58%)   ← 사용자가 겪는 값
통화 도중 '주의' 이상          3건  (1.74%)

최종은 안전인데 도중에 경고가 뜬 통화: 없음
```

**둘이 같다.** 증거를 누적하는 구조라 점수가 뒤로 갈수록 오르기만 하고,
중간에 튀었다가 내려가는 일이 없다. 설계가 의도한 대로 동작했다는 뜻이고,
이건 **재보기 전에는 알 수 없던 것**이다.

### ② 실제 발생률에서는 정밀도가 무너진다

지금까지 평가 세트는 사기:정상이 대략 1:1이었다. **실사용은 그 비율이 아니다.**
오탐률 0.58%는 낮아 보이지만, 사기가 드물면 헛경고가 진짜 경고를 압도한다.

```
탐지율 99.3% (134/135)    오탐률 0.58%
```

| 통화 1000건 중 사기 | 경고 횟수 | 진짜 | 헛경고 | **경고가 진짜일 확률** |
|---:|---:|---:|---:|---:|
| 500건 (평가 세트 구성) | 499 | 496 | 2.9 | 99.4% |
| 100건 | 105 | 99 | 5.2 | 95.0% |
| 20건 | 25 | 20 | 5.7 | 77.7% |
| 5건 | 11 | 5 | 5.8 | 46.2% |
| **1건 (모든 통화 대상)** | 6.8 | 1.0 | 5.8 | **14.6%** |

**모든 통화에 항상 켜두면 경고 일곱 번 중 한 번만 진짜다.**
이건 성능 문제가 아니라 **산수**다. 탐지율을 아무리 올려도 바뀌지 않는다.

### 그래서 이 프로그램이 가치를 가지려면

숫자가 말하는 결론은 분명하다 — **모든 통화에 켜면 안 된다.**

| | 사기 비율 | 정밀도 |
|---|---:|---:|
| 모든 통화 | ~1/1000 | 14.6% |
| **모르는 번호만** | ~20/1000 | **77.7%** |
| 사용자가 이상하다고 느껴 켤 때 | ~100/1000 | 95.0% |

같은 프로그램인데 **언제 켜느냐로 정밀도가 14%와 95% 사이를 오간다.**
발신번호 필터(모르는 번호·국제전화·변작 의심)를 앞에 두는 것이
탐지 로직을 더 다듬는 것보다 훨씬 크게 작동한다.

절대량으로 보면 이렇다. 정상 통화 1000건에 헛경고 **5.8회**다.
하루 10통씩 100일이면 **17일에 한 번** 헛경고를 겪는다.
고령자처럼 통화가 적으면 더 드물다. 감당할 수 없는 수준은 아니지만,
"오탐률 0%"라고 말하는 것과는 전혀 다른 이야기다.

50% 정밀도를 모든 통화에서 얻으려면 오탐률이 **0.099%** 여야 한다 —
지금의 6분의 1이다. 그게 다음 목표선이다.

### 11차에서 고친 것 — 프레임이 문장을 넘어간다

미탐 하나가 나왔다(R11-F12, 노인 대상 방문 수령).

> "제가 대신 신청해 드릴 테니 **통장이랑 도장 준비해 두세요**"
> "이따 **직원이 방문하면 건네주시면** 됩니다"

대면편취 프레임의 두 자리가 **다른 마디에** 있었다. 프레임이 문장 단위로 돌아
통째로 비켜 갔다. 자연스러운 말하기 방식이지 회피가 아니다 —
한 문장에 다 넣는 쪽이 오히려 부자연스럽다.

그래서 **자리를 따로 세고 통화 단위로 합치게** 바꿨다(`CALL_FRAMES`).
증거 누적과 같은 구조다. 어느 마디에서 채워졌든 통화가 끝날 때 자리가 다 차면
프레임이 성립한다. 현금뿐 아니라 통장·카드·도장을 그대로 받아 가는 유형도
같은 자리에 넣었다 — 고령층에서 특히 많다.

```
검증셋 11  탐지 91.7% → 100.0%   오탐 0.0% 유지
```

| | 첫 탐지율 | 첫 오탐률 | 찾아낸 실제 결함 |

**다섯 번 만들어 다섯 번 다 실제 결함이 나왔다.** 오탐률은 42.9 → 20.0 →
18.2 → 18.2 → 16.7%로 줄었지만 **0에 수렴하지 않는다.**
탐지율은 5차에서 오히려 가장 낮았다(75.0%). 새 공격 각도를 잡을 때마다
안 보이던 구멍이 계속 드러난다.

성격은 5차에서 바뀌었고 6차가 그것을 확인했다. 4차까지는 **잡는 방식 자체가
없어서** 뚫렸다(고지 문구, 경고 맥락, 은행 사칭). 5·6차에서 뚫린 것은
**닫힌 집합에 어휘가 없어서**이거나 **내가 직전에 만든 구멍**이었다.

6차에서 오탐이 처음으로 0이 됐고, 통화 구조 공격은 전부 막혔으며,
예측이 처음으로 맞았다. 구조는 어느 정도 자리를 잡았다는 뜻이다.

다만 **6차의 미탐 두 건은 내가 5차에서 만든 구멍이었다.** 이게 가장 오래 남을
교훈이다 — 검증셋이 찾아내는 결함의 상당수는 **직전 수정이 만든 것**이다.
고칠 때마다 새 셋으로 확인하지 않으면 알 수 없다.

7차가 그 교훈을 그대로 재현했고, 8차도 마찬가지였다.
실패의 대부분이 직전 수정 탓이었다.

8차에서는 그것이 한 걸음 더 나아갔다 — **고치는 방식 자체가 한계에 닿았다.**
7차에서 `래서`를 앞 글자 가드로 막았는데, 8차에서 같은 충돌이 셋 더 나왔고
그중 `라고`·`다고`는 가드를 걸 수 없는 어미였다(가장 흔한 인용 어미라
진짜 인용을 통째로 잃는다). 개별 어미에 예외를 다는 층위를 버리고
**표현을 지우는 층위**로 옮겨야 했다.

같은 결함이 세 번 반복되면 그건 어휘 문제가 아니라 **층위 문제**다.
1~4차에서 열거 → 형태 규칙으로 옮긴 것과 같은 종류의 전환이다.

9차가 그것을 한 번 더 확인했다. 8차의 해법이 다시 열거였고, 나는 그것을
8차 말미에 **스스로 지목해 두었다** — "1차에서 겪은 것과 똑같은 자리에 있다".
9차에서 지시대명사만 바꾼 공격에 그대로 뚫렸다. 예고한 자리가 예고한 대로
터진 것이다.

**같은 실수를 알면서도 반복한다는 것이 이 기록의 가장 정직한 부분이다.**
급할 때 손이 먼저 가는 곳은 언제나 열거이고, 구성으로 옮기는 데는
한 번 더 뚫려 보는 과정이 필요했다.
그리고 7차에서 가장 값진 발견은 `래서`였다 —
**넣으면 회피로가 되고 빼면 피해자를 잡는** 표지였다.
이런 것은 양쪽을 다 겪어 봐야 보인다. 한 번의 검증으로는 절대 안 나온다.

그리고 4차는 3차가 만든 규칙(C6)을 깎아냈다. **한 검증셋의 수정이 다음
검증셋의 결함이 되는 일이 실제로 일어난다.** 다섯 번째를 만들면 또 나온다고
보는 편이 맞다.

되풀이해서 나온 결함의 성격도 하나로 모인다 —
**빠진 것은 사기 수법이 아니라 한국어 형태였다.**
어절 사이 조사 삽입, 높임 조사 '께', '말하지'는 있고 '알리지'는 없음.
사기범이 노려서 쓴 회피가 아니라 그냥 말하면 나오는 형태들이다.

그리고 **세 검증셋 모두 이제 훈련셋이다.** 결과를 보고 규칙을 고쳤기 때문이다.
정직하게 인용할 수 있는 검증 숫자는 각 셋의 **첫 실행 값**뿐이다.

## 형태론으로 옮겼다 — 표현을 세지 말고 구성을 세라

네 번의 검증셋이 같은 결론을 가리켰다.
**빠진 것은 사기 수법이 아니라 한국어 형태였다.**

| 놓친 문장 | 빠진 것 | 발견 |
|---|---|---|
| "가족에게 이 사실을 알리지 마세요" | 어절 사이 삽입 | 1차 |
| "형수님한테는 말하지 말고" | 임의의 호칭 | 1차 |
| "창구 직원에게는 말씀하지 마세요" | 말하 → 말씀하 | 3차 |
| "부모님께는 알리지 마세요" | 높임 조사 '께', '알리' 어간 | 4차 |

넷 다 사기범의 회피가 아니다. **그냥 말하면 이렇게 된다.**
그때마다 표현을 하나씩 더 넣었지만 한국어는 교착어라 끝이 없다.

이 결함들은 전부 **생산적 구성**이다. 열린 자리와 닫힌 자리로 되어 있고,
닫힌 자리는 셀 수 있다.

```
[대상]  +  에게/한테/께/에 (는/도/만)  +  …  +  말하/알리/말씀하/…  +  지 마/면 안
 열림              닫힘 5·4개                     닫힘 13개            닫힘 8개
```

**열린 자리를 요구하지 않는 것이 핵심**이다. 호칭은 무한하다 —
형수님·아드님·사모님·과장님·담당자님. 그래서 호칭을 빼고 나머지로 잡는다.

닫힌 자리를 곱하면 표면형이 수천 개다. 문자열로 다 찾으면 비용이 감당이
안 되므로 정규식 하나로 컴파일한다(`mirinae/mode1/morphology.py`).
정규화된(공백 없는) 텍스트 위에서 돌기 때문에 **띄어쓰기 변수가 통째로 사라지고**,
문자 인덱스가 곧 음절 인덱스라 인용·고지·서술 판정이 키워드와 똑같이 적용된다.

규칙은 둘이다.

| 규칙 | 구성 | 잡는 것 |
|---|---|---|
| `M-S4-함구` | 여격 조사 + 함구 동사 + 부정 어미 | 고립 유도 |
| `M-S5-지정계좌` | 지정 동사 + **겸양** 보조동사 + 관형형 + 목적지 | 화자가 즉석 지정하는 계좌 |

두 번째 규칙이 겸양 `-드리-`만 인정하고 존경 `-시-`는 인정하지 않는 것이
방향을 가른다. `계좌번호 알려주시면`(청자가 준다 · 정상)과
`제가 알려드리는 계좌로`(화자가 준다 · 사기)가 문법으로 갈린다.

### 일반화가 실제로 되는지 재봤다

주장은 "표현을 나열하지 않아도 잡는다"이고, 그건 **DB에 한 번도 적지 않은
형태**로만 검증된다. 호칭 8 × 조사 5 × 동사구 7을 곱해 DB 표현이 들어가지
않은 조합 280개를 만들어 넣었다.

```
280개 중 280개 탐지 (100.0%)

  사위보고 이야기하지 마              며느리보고 말씀하지 않으셔야
  옆집 아저씨에게만 밝히지 마십시오    이모에게는 이야기하지 마
```

반대쪽도 재야 한다. 손으로 쓴 정상 문장에서 **오탐이 하나 나왔다** —
"친구한테는 말했지만 다른 사람에겐 안 했어".

그런데 원인은 형태 규칙이 아니라 **열거로 넣어 둔 키워드**였다.
`한테는 말하지`가 `한테는 말했지`와 자모 거리 2로 근사 매칭됐다.

> **표현을 나열하면 근사매칭에 기대야 하고, 근사매칭은 반드시 값을 치른다.**
> 형태 규칙은 부정 어미 `-지 마/말/않`을 명시적으로 요구하므로
> "말했지만"과 "말하지 마"를 정확히 가른다.

그래서 형태 규칙이 대체하는 열거 표현 둘을 **지웠다**. 오탐이 사라지고
탐지는 그대로였다. DB가 줄면서 성능이 좋아지는 방향이다.

비용은 발화당 **0.25 ms**다(39.77 → 40.02 ms). 정규식이라 패턴당 한 번만 훑는다.

### 다섯 세트 전부

| | 훈련(57) | 검증1(13) | 검증2(20) | 검증3(22) | 검증4(21) |
|---|---:|---:|---:|---:|---:|
| 탐지율 | 100.0% | 100.0% | 90.0% | **100.0%** | 100.0% |

검증셋 3차의 탐지율이 90.9 → 100.0%로 올랐다. 형태 규칙을 넣으며
**그 셋을 다시 보지 않았는데도** 남아 있던 미탐(T-F-09 부고 조의금)이 잡혔다.
표현을 맞춰 넣은 것이 아니라 구성을 잡았기 때문이다.

STT 오차 10%에서 탐지 94.3% · 오탐 3.9% · 회피 3.3%. 테스트 113건 통과.

### 남은 것

형태소 분석기가 아니다. 어간을 진짜로 자르는 것이 아니라 **어간의 표기를
열거**하고 뒤에 올 수 있는 것을 제한할 뿐이다. `말씀하`를 적어야 `말씀하`를 잡는다.
다만 이제 **어간 하나를 적으면 그 어간의 모든 활용형이 함께 온다** —
조사 5 × 보조사 4 × 어미 8 = 160가지가 한 줄로 들어온다.

다음에 결함이 나온다면 그건 새 **어간**이지 새 활용형은 아닐 것이다.
그리고 어간은 활용형보다 훨씬 적다.

시나리오는 깨끗한 텍스트다. 실제로는 Whisper가 틀린다.

## 딥보이스 탐지 (P1) — 측정했고, 못 쓴다

D08 §03 4단계 항목이다. 설계도가 이렇게 예고했다.

> "ASVspoof 모델은 학습에 없던 합성 방식에 일반화가 약하다. XTTS-v2를 못 잡을 수 있다.
>  P1이므로 실패 시 제외하고 한계로 기술"

사전학습 탐지기(`MelodyMachine/Deepfake-audio-detection-V2`, wav2vec2 기반 fake/real 2분류)를
붙이고 **우리가 실제로 방어하려는 XTTS-v2 합성음 16개로 측정했다.**

| 조건 | n | 재현율 |
|---|---|---|
| XTTS-v2 합성음 | 16 | **18.8%** (3/16) |

**예고된 대로 실패했다.** 그런데 실패의 양상이 더 나쁘다.

```
clone_from_original_0.wav   fake=1.0000   딥보이스 의심
clone_from_original_1.wav   fake=0.9997   딥보이스 의심
clone_from_original_2.wav   fake=0.0000   정상 음성      ← 같은 조건
clone_from_original_3.wav   fake=0.9973   딥보이스 의심
clone_from_original_4.wav   fake=0.0000   정상 음성      ← 같은 조건
```

완전히 같은 입력·같은 설정으로 만든 5개인데 판정이 1.0000과 0.0000으로 갈렸다.
**중간값이 없는 양극단 분포**라, 임계값을 조정해서 해결할 수 있는 문제가 아니다.

흥미로운 부수 관찰 — 잡음이나 섭동이 섞인 음성(C-B 대조군, 보호본)에서 나온 복제는
**전부** fake≈0으로 나왔다. 탐지기가 붙잡는 인공물이 그런 처리에 쉽게 지워진다는 뜻이다.

### 탐지기를 교체했다 — 재현율 36% → 82%

같은 XTTS 표본 11개로 대안 모델을 비교했다.

재현율만 오른 게 아니라 **판정이 일관적**이다. 기존 모델은 완전히 같은 조건에서 만든
복제음에 1.0000과 0.0000을 내는 양극단 분포였다 — 임계값 조정으로 해결할 수 없는 형태다.

**그래도 기본값은 여전히 꺼짐이다.** 아래 이유가 그대로 남아 있다.

## C-D 대조군 확보 — 이제 SRS를 해석할 수 있다

지금까지 SRS 수치를 **해석할 수 없었다.**

> 보호본의 SRS가 0.63이다. → 그래서 좋은 건가?

답할 수 없었다. **서로 다른 두 사람의 SRS가 얼마인지 몰랐기 때문이다.**
그 값이 0.8이면 0.63은 "남남보다 더 멀어졌다"는 강한 주장이고,
0.3이면 "여전히 같은 사람으로 들린다"는 뜻이다. 정반대 결론이 같은 숫자에서 나온다.

`metrics.dsr()`은 임계값을 인자로 받는데 그 임계값을 만들 대조군이 없었고,
`pipeline.PROVISIONAL_THRESHOLD = 0.75`는 **근거 없이 정한 숫자**였다.

```bash
.venv-xtts\Scripts\python make_speakers.py -o out/speakers -n 6   # 화자 6명 생성
python calibrate_dsr.py out/speakers                              # 두 분포를 잰다
```

| 분포 | 조각쌍 | 평균 | 범위 |
|---|---|---|---|
| 같은 화자 (다른 조각) | 116 | 0.8622 ±0.0331 | [0.752, 0.937] |
| **타 화자 (C-D)** | 664 | **0.5962 ±0.0944** | [0.375, 0.871] |

**EER 지점 0.7962 · 동일오류율 4.3%.**
동일오류율이 4.3%면 이 인코더는 화자를 잘 가른다 — 임계값을 믿고 쓸 수 있다.
옛 0.75는 우연히 가까웠지만 그건 운이었지 근거가 아니었다.

### 방법론에서 한 번 틀렸다

처음에는 같은 화자를 3초 조각으로, 타 화자를 **전체 파일로** 쟀다.
임베딩은 입력이 길수록 안정되고 유사도가 높게 나오므로,
"같은 사람이라 비슷한 것"과 "길어서 비슷한 것"이 섞인다.
지금은 모든 음성을 같은 길이로 잘라 같은 풀에서 쌍을 만든다.
고친 뒤 타 화자 평균이 0.6695 → 0.5962로 내려갔다 — 앞의 값은 길이 때문에 부풀어 있었다.

임계값도 처음엔 타 화자 상위 95백분위를 쓰려 했는데 **그만뒀다.**
"가장 닮은 남남 쌍"에 맞춘 느슨한 기준이라 우리 결과를 유리하게 만든다.
자기 성과가 좋아 보이는 방향으로 기준선을 고르는 것은 측정이 아니다.

| 조건 | SRS | 임계값 0.7962 기준 |
|---|---|---|
| **보호본** | **0.6342** | **타 화자 판정** ✓ |
| C-B 대역제한잡음 | 0.7685 | 타 화자 판정 (겨우) |
| C-A 백색잡음 | 0.8052 | 실패 |
| C-E 셔플 섭동 | 0.8898 | 실패 |
| C-C 무섭동 | 1.0000 | 인코더 정상 확인 |

C-E가 0.890으로 거의 무효인 반면 최적화된 섭동은 0.634 —
**효과의 원인이 크기가 아니라 구조**임을 지지한다. 이게 가장 강한 카드다.

**다만 이 성공은 공짜가 아니다.** 그리고 그 대가를 우리는 **실제보다 작게 보고하고 있었다.**

```
제약 기준 (thr × 3.0)   최대 초과 12.24 dB · 위반  2.44%   ← 파이프라인이 보고하던 값
절대 기준 (thr × 1.0)   최대 초과 21.78 dB · 위반 20.30%   ← 실제로 들리는 정도
```

같은 파일인데 "bin의 2.4%가 임계값 위"와 "**20.3%가 위**"로 갈린다.
배율 3.0은 **"안 들린다"는 보장을 포기한 지점**이고, 포기한 정도가 생각보다 크다.
"인코더를 무너뜨렸다"와 "안 들린다"를 동시에 주장할 수 없다.
청취 평가로 가청도 상한을 먼저 정하고 거기서 배율을 역산해야 한다(D07 W1).

### 가청도 지표를 잘못 읽고 있었다 — 결함 5

`audibility(delta, thr, ratio, model)`은 `thr × ratio`를 기준선으로 초과량을 잰다.
즉 **배율마다 자기 기준이 달라진다.** 배율을 키우면 기준선도 함께 올라가므로
초과량이 **줄어든다.** 스윕 표에서 이렇게 보였다.

| 배율 | 제약 기준 초과 | 절대 기준 초과 | 절대 위반% |
|---|---|---|---|
| 0.75 | 14.5 dB | 12.0 dB | **0.44%** |
| 1.50 | 11.8 dB | 15.3 dB | 17.78% |
| 3.00 | 13.3 dB | 22.9 dB | 23.45% |
| 6.00 | 12.2 dB | 27.7 dB | 24.48% |
| 10.00 | **9.7 dB** | **29.7 dB** | **24.28%** |

제약 기준 열은 배율이 커져도 14.5 → 9.7로 **줄어든다.**
그대로 읽으면 "배율을 올릴수록 덜 들린다"가 되는데, 절대 기준으로는 정반대다 —
초과량이 12.0 → 29.7 dB로 늘고 위반 bin이 0.44%에서 24.3%로 **55배**가 된다.

D09가 마스킹 배율을 "청취 평가로 결정"하도록 열어 둔 파라미터인데,
그 결정을 뒷받침해야 할 지표가 배율 간 비교에 쓸 수 없는 값이었다.
**에러 없이 조용히 틀리는 종류**이고, 결론을 정확히 반대로 이끈다.

→ `pipeline.ProtectionResult`가 이제 두 기준을 모두 들고 다니고(`audibility_abs`),
   리포트는 **절대 기준을 먼저** 찍는다. `sweep_params.py`도 두 열을 나란히 낸다.

**복제 단계 — 실제로 막아야 하는 것.**

| 조건 | n | 평균 SRS | **DSR** | 95% CI |
|---|---|---|---|---|
| 원본 (기준선) | 5 | 0.9524 | 0% | [0.0, 43.4] |
| 보호본 | 5 | 0.9122 | **0%** | [0.0, 43.4] |
| C-B 대역제한잡음 | 5 | 0.8566 | **0%** | [0.0, 43.4] |

**어느 조건도 복제를 막지 못했다.** 보호본이든 잡음이든 복제음은 전부
임계값 위에 남아 "같은 사람"으로 판정된다.

두 표를 나란히 놓은 것이 이 프로젝트의 핵심 발견이다 —
**인코더는 무너뜨렸지만 복제는 못 막았다.** 이제 그 문장이 근거 있는 임계값을 가진다.
제로샷 복제 모델이 화자 임베딩 하나로 음색을 결정하지 않는다는 뜻이고,
임베딩 표적 방어가 이 세대 모델에 구조적 한계가 있다는 정량적 증거다.

**한계** — 대상이 XTTS 합성 화자다. 합성 화자끼리의 거리가 사람끼리의 거리와
같다는 보장이 없다. 임계값은 여전히 잠정값이고, 팀원 녹음이 오면 같은 명령을 다시 돌린다.

## 통화 채널 — 가장 중요했던 미검증 전제 (결함 6)

미리내는 **전화 통화용**인데, 지금까지의 모든 SRS는 **파일 대 파일**로 잰 값이었다.
실제 경로에는 통화 채널이 끼어 있다.

```
보호된 음성 → [300~3400 Hz · 8 kHz · G.711] → 상대방 → 녹음 → 복제
```

README에 "협대역 8 kHz에서 최대 33%p 손실 예상"이라고 **예상만** 적혀 있었다.
`mirinae/codec.py` + `codec_test.py`로 실제로 쟀다.

```bash
python codec_test.py out/ref
```

| 대상 | SRS 전 | SRS 후 | 변화 | 섭동 잔존 | 구조 상관 |
|---|---|---|---|---|---|
| **보호본** | 0.6342 | **0.8346** | **+0.2004** | 101.2% | 0.989 |
| C-A 백색잡음 | 0.8052 | 0.7464 | -0.0588 | 39.0% | 0.623 |
| C-B 대역제한잡음 | 0.7685 | 0.6620 | -0.1065 | 97.9% | 0.988 |
| C-E 셔플 섭동 | 0.8898 | 0.8591 | -0.0306 | 100.1% | 0.989 |

**보호본만 방어가 무너진다.** 판정 임계값 0.7962를 넘어 "같은 화자"로 되돌아왔다.
잡음 대조군은 오히려 채널 통과 후 **더 잘 막는다**(SRS가 내려간다).

### 원인은 코덱이 아니었다

처음 예상은 "코덱이 섭동을 지운다"였다. 마스킹 아래 숨긴 성분과 코덱이 버리는 성분이
같은 것이므로 합리적인 예상이었다. **틀렸다.**

```
섭동 잔존 101.2% · 구조 상관 0.989
```

섭동은 그대로 남아 있다. 단계별로 끊어 보면 **대역 제한만으로 이미 무너진다.**

| 채널 단계 | 보호본 SRS |
|---|---|
| 무처리 | 0.6342 |
| 대역 제한만 | **0.8420** ← 여기서 끝난다 |
| + 8 kHz | 0.8405 |
| + G.711 μ-law | 0.8346 |

진짜 원인은 이것이다. 섭동은 **전대역 원본**의 임베딩에서 멀어지도록 최적화된다.
그런데 채널이 원본을 300~3400 Hz로 자르면 그 임베딩이 크게 이동한다
(원본↔채널통과원본 SRS 0.7478). 전대역 원본에 대해 계산한 적대적 방향은
채널 통과본에 대해서는 더 이상 적대적이지 않다.

**섭동이 지워진 게 아니라 표적이 틀렸다.**

### 고친 방법 — 채널을 최적화 루프 안으로

`PGDConfig.channel_aware`가 손실을 이렇게 바꾼다.

```
이전:  encoder(x + δ)          대  encoder(x)
이후:  encoder(channel(x + δ)) 대  encoder(channel(x))
```

즉 "상대방이 실제로 듣게 될 신호"에서 멀어지도록 최적화한다.
루프 안에서는 미분 가능한 대역 제한으로 채널을 근사하고
(실측상 대역 제한이 지배적이고 μ-law는 미분이 안 된다),
**검증은 `codec_test.py`가 진짜 코덱으로 한다** —
근사로 최적화하고 근사로 검증하면 아무것도 증명하지 못한다.

효과는 `channel_ab.py`가 같은 시드로 켬/끔을 나란히 돌려 잰다.

```bash
python channel_ab.py out/reference.wav --repeat 5 --steps 100
```

대조군(채널 통과 후): C-A 0.7651 ±0.0059 · **C-B 0.6933 ±0.0126** (이겨야 할 값)

| 설정 | 채널 통과 후 SRS | 판정 | 채널 **전** SRS |
|---|---|---|---|
| 채널 인지 끔 | 0.7658 ±0.0183 | 타 화자 (아슬) | 0.4020 |
| **채널 인지 켬** | **0.4627 ±0.0365** | **타 화자** | 0.9134 |

**+0.3031 · 신뢰구간 분리.** 그리고 이것이 중요하다 —
**채널 통과 후에도 대조군을 이긴 것은 이번이 처음이다** (0.4627 < 0.6933).
그전까지 통화 경로에서는 적대적 섭동이 대역제한잡음보다 못했다.

표의 마지막 열이 이 방법의 성격을 그대로 보여준다.
채널 인지 섭동은 **깨끗한 파일에서는 거의 무효**다(0.9134).
채널을 통과해야 비로소 적대적이 된다 — 표적을 바꿨으니 당연한 결과이고,
"파일로 재면 좋아 보이는데 통화에서는 안 되는" 이전 상태의 정확한 반대다.

**어느 쪽을 기본값으로 둘 것인가.** 미리내의 위협 모델은 통화 녹취이므로
`CHANNEL_AWARE = True`를 기본으로 둔다. 파일이 직접 유출되는 경우
(메신저 음성메시지 등)를 함께 막으려면 두 목표를 섞어야 하고,
그건 아직 측정하지 않았다.

## 복제 게이트 — 아직 열리지 않았다

계획서(D07 §04)가 UI보다 먼저 닫으라고 못박은 관문이다.
**보호본을 XTTS-v2에 넣었는데 복제가 성공하면 시연 영상의 클라이맥스가 사라진다.**

측정 구조는 같은 문장을 두 번 복제해 나란히 놓는 것이다.
원본에서 뽑은 복제는 잘 되어야 하고(기준선), 보호본에서 뽑은 복제는 실패해야 한다.
기준선까지 낮으면 XTTS가 애초에 그 목소리를 복제하지 못한 것이라 아무것도 주장할 수 없다.

### 시도 기록

| 시도 | 표적 | 표적 인코더 SRS | **복제음 SRS** | 하락 | 판정 |
|---|---|---|---|---|---|
| ① 전이 | Resemblyzer | 0.634 | **0.9135** | 0.037 | 실패 |
| ② 화이트박스 | XTTS speaker_encoder | 0.465 | **0.8933** | 0.047 | 실패 |
| ③ 이중 경로 | speaker_encoder + gpt_cond | 0.486 | **0.9058** | 0.027 | 실패 |

기준선(원본 복제) 0.933~0.950 · 대조군 C-B(대역제한잡음) 0.866~0.881

**세 번 모두 C-B 대역제한잡음이 우리 섭동보다 복제를 더 방해했다.**

### n=5 반복 측정 — 이것이 현재 가장 신뢰할 수 있는 수치다

위 표는 전부 n=1이라 생성 편차와 효과를 구별하지 못한다. 조건당 5회 복제해 다시 쟀다.
(대상: 시도 ③의 보호본 · `measure_clones.py`)

| 조건 | n | 평균 SRS | 표준편차 | 95% CI |
|---|---|---|---|---|
| 원본 (기준선) | 5 | 0.9524 | 0.0047 | ±0.0041 |
| **보호본** | 5 | **0.9122** | 0.0173 | ±0.0151 |
| C-B 대역제한잡음 | 5 | **0.8566** | 0.0196 | ±0.0172 |

**① 방어 효과는 실재한다.** 원본 [0.9482, 0.9565]과 보호본 [0.8971, 0.9273]의
신뢰구간이 겹치지 않는다. 하락 0.0402는 생성 편차로 설명되지 않는다.

**② 그러나 단순 잡음보다 못하다.** C-B(0.8566)와 보호본(0.9122)의 구간도 겹치지 않는다.
**같은 SNR의 대역제한 잡음이 적대적 섭동보다 유의하게 더 복제를 방해한다.**
적대적 최적화의 이점이 이 모델에서는 나타나지 않는다는 뜻이다.

**③ n=1은 실제로 위험했다.** 시도 ③에서 원본 단일 측정은 0.9332였는데
n=5 평균은 0.9524다. 그 한 번이 낮은 쪽 이상치였다. 반복 없이는 판정이 뒤집힌다.

### 그런데 n=1 표를 그대로 믿으면 안 된다

C-C 대조군은 **원본과 완전히 같은 오디오**다(δ=0). 그런데 복제 결과가 다르게 나온다.

| 실행 | 원본 | C-C (같은 파일) | 차이 |
|---|---|---|---|
| ① | 0.9501 | 0.9444 | 0.0057 |
| ② | 0.9403 | 0.9328 | 0.0075 |
| ③ | 0.9332 | 0.9520 | 0.0188 |

XTTS 생성이 확률적이라 같은 입력에도 결과가 흔들린다. 이 흔들림이 **0.006~0.019**인데
보호에 의한 하락은 **0.027~0.047**이다. 같은 자릿수다.

즉 **n=1로 잰 위 판정들은 효과와 생성 편차를 구별하지 못한다.**
"하락했다"고 말하려면 반복 측정과 신뢰구간이 있어야 한다 —
D09 §06이 "n · 신뢰구간 · 대조군 대비 셋이 항상 함께 나온다"고 못박은 것이 바로 이 문제다.

`clone_test.py --repeat 5`가 이를 처리한다. 조건마다 여러 번 복제해 평균과 95% CI를 내고,
원본 대 C-C 차이를 **생성 편차 기준선**으로 함께 보고한다.
하락폭이 그 기준선의 1.5배 이하면 "판정 불가 · 효과가 노이즈 수준"으로 판정한다.

### 무엇을 알아냈나

**① 신호 도메인 섭동은 인코더 간 전이가 되지 않는다.**
Resemblyzer 기준으로 SRS 0.634까지 무너뜨린 섭동이 XTTS에서는 0.9135였다.
잡음 대조군(0.8806)보다도 못했다. D09 §01이 "블랙박스 전이 공격"으로 우려한 그대로다.

**② XTTS conditioning은 블랙박스가 아니다.**
D09 §01은 "비공개 · gradient 접근 여부가 최대 리스크"로 적었지만,
가중치가 공개되어 있어 두 경로 모두 화이트박스로 열린다.

    hifigan_decoder.speaker_encoder(wav_16k, l2_norm=True) → (512,)   grad norm 1.08e+01
    gpt.get_style_emb(wav_to_mel_cloning(wav_22k))          → (1024,)  grad norm 2.06e-02

**③ 화자 임베딩을 무너뜨려도 복제는 성공한다 — 이게 핵심 발견이다.**
XTTS speaker_encoder 임베딩을 SRS 0.465까지(원본과 거의 무관한 방향으로) 밀어냈는데
실제 복제음은 원본과 0.8933이었다. **화자 임베딩이 음색을 결정하는 유일한 경로가 아니다.**
그래서 GPT 조건 latent를 함께 공략하는 시도 ③으로 넘어갔다.

### 이 결과를 어떻게 다룰 것인가

D07 리스크표는 SEV1 대응을 이렇게 정해 두었다 —
마스킹 배율 상향 → 앙상블 확대 → 그래도 안 되면 주장을 "임베딩 교란 확인"으로 좁힌다.

여기에 더해 짚어둘 것이 있다. **부정적 결과도 그 자체로 기여다.**
"제로샷 복제 모델은 화자 임베딩 하나로 음색을 결정하지 않으며,
따라서 임베딩 표적 방어는 이 세대 모델에 구조적 한계가 있다"는 정량적 발견은
통신사 인프라 협력이 왜 필요한지에 대한 근거가 된다.
숫자를 숨기고 성공한 것처럼 발표하는 것이 훨씬 나쁘다.

**단서** — 지금까지의 측정은 전부 XTTS가 만든 음성을 대상으로 했다.
XTTS 입장에서 분포 안쪽이라 복제가 유난히 쉬운 조건이고(기준선 0.95),
사람 목소리에서는 기준선이 낮아 하락폭이 더 크게 보일 수 있다.
**게이트의 진짜 판정은 팀원 녹음으로만 가능하다.**

## 청크 분할이 방어를 무너뜨린다 — 설계 변경

가장 오래 걸려 찾은 결함이다. **모드 2는 원래 방어가 성립하지 않았다.**

2초 청크로 쪼개 각각 최적화하면, 청크마다 "자기 임베딩에서 멀어지는" 방향이
제각각으로 잡힌다. 복제 모델은 파일 **전체**를 하나로 보므로 그 방향들이
서로 상쇄된다. 청크 단위로는 잘 밀리는데 합쳐 놓으면 안 밀린다.

실사용 녹음 14초 · 60스텝 · SNR 20 dB · **같은 기준으로 재측정**:

| | 파일 기준 SRS | 통화 채널 통과 후 | 소요 |
|---|---|---|---|
| 청크 스트리밍 | 0.9427 | 0.8045 — 임계값 0.7962 **위. 실패** | 763초 |
| 전체 발화 일괄 | 0.8097 | **0.3709** — 성공 | 56초 |

방어가 되면서 13배 빠르다. 잘라 붙이기에 약하지도 않다 —
보호본에서 잘라낸 발췌의 SRS는 2초 0.8213 / 4초 0.7900 / 8초 0.8014로
전체(0.8097)와 같은 수준이다.

> **측정 실수 기록.** 처음에는 전체 0.2658(대역제한 근사)과 청크 0.8045(실제 코덱)를
> 비교해 "3배 개선"이라고 적었다. **기준이 서로 달랐다.** 같은 기준으로 다시 재니
> 0.8045 대 0.3709 — 결론은 살았지만 숫자는 틀렸었다.

대가는 **실시간 주입을 포기한 것**이다. 녹음이 끝나야 시작할 수 있다.
되지도 않는 실시간을 흉내내는 것보다 되는 방어를 주는 편이 낫다고 판단했다.

## 성능

전체 발화 일괄 기준, CPU(Intel Ultra 7 258V)에서 **6초 녹음 · 60스텝에 약 61초**.
14초 녹음이 56초였으니 길이보다 스텝 수에 더 좌우된다.
한 스텝의 95% 이상이 인코더 forward+backward다(CPU 85~145 ms).

스텝 수를 늘려도 방어는 더 강해지지 않는다 — 15/60/200 스텝이 모두 SRS ≈0.81로
포화한다. **GPU의 이득은 "더 강한 방어"가 아니라 "같은 방어를 더 빨리"** 다.
`time_budget_sec`으로 장비에 맞춰 스텝 수가 자동 조절된다.

모드 1은 CPU에서도 동작한다(faster-whisper base · int8).

## 모드 2 강화 — 전이성이 없었다

모드 2는 SRS를 0.37까지 떨어뜨리는데 **실제 복제 저지율(DSR)은 0%** 였다.
화자 검증기는 속이는데 복제 모델은 안 속는다. 이 모순을 여태 설명하지 못했다.

### 진단 — 인코더 하나에만 최적화하고 있었다

`encoder.py`의 `EncoderEnsemble` 주석에 이미 답이 적혀 있었다 —
"한 모델만 속이면 방어가 아니라 과적합이다." 자리만 열어 두고 구현하지 않았다.

독립적인 인코더(ECAPA-TDNN · SpeechBrain · VoxCeleb)를 붙여 기존 보호본을 재측정했다.

| 보호본 | Resemblyzer (최적화 대상) | ECAPA-TDNN (미학습) |
|---|---:|---:|
| `out/ref` | **0.6342** ✓ | **0.8131** ✗ |

판정 임계값은 0.7962다. **한쪽은 통과하고 다른 쪽은 실패한다.**
복제 모델(XTTS·GPT-SoVITS)은 Resemblyzer를 쓰지 않으므로,
Resemblyzer의 임베딩 공간에서만 멀어진 섭동은 그들에게 아무 의미가 없다.

DSR 0%의 원인이 이것이었다. 성능 부족이 아니라 **표적을 잘못 잡은 것**이다.

### 왜 ECAPA-TDNN인가

겹치는 곳이 최소한이어야 앙상블의 의미가 있다.

| | Resemblyzer (GE2E) | ECAPA-TDNN |
|---|---|---|
| 구조 | 3층 LSTM | TDNN + SE-Res2Block + attentive pooling |
| 특징 | 선형 power mel 40 | log mel-fbank 80 |
| 학습 | LibriSpeech 계열 | VoxCeleb 1+2 |
| 임베딩 | 256차원 | 192차원 |

`encode_batch()`는 내부에서 gradient를 끊을 수 있어 하위 모듈
(`compute_features` → `mean_var_norm` → `embedding_model`)을 직접 부르는
미분 경로를 따로 짰다. **공식 경로와 대조해 오차 0.00e+00을 확인**했다 —
Resemblyzer에서 했던 것과 같은 절차다. 다시 짠 경로를 대조하지 않으면
엉뚱한 방향으로 최적화하면서도 숫자는 좋아 보인다.

### 결과 — 앙상블이 전이성을 만든다

8초 발화 · SNR 20 dB · 통화 채널 통과 후:

| 최적화 | 채널후 Resemblyzer | 채널후 ECAPA |
|---|---:|---:|
| 단독 (Resemblyzer) 40스텝 | 0.5557 ✓ | **0.8265 ✗** |
| 앙상블 40스텝 | 0.7780 ✓ | **0.5094 ✓** |
| 앙상블 150스텝 | **0.7161 ✓** | **0.5276 ✓** |

**단독은 미학습 인코더에서 실패하고 앙상블은 양쪽 다 임계값 아래로 내린다.**
40스텝에서 Resemblyzer가 0.778로 간신히 통과하는 것은 예산을 둘로 나누기
때문이고, 150스텝에서 0.716까지 내려간다.

대가는 시간이다. 같은 스텝 수에서 **4배 이상** 걸린다(40스텝 5초 → 22초, CPU).
그래도 바꿨다 — **전이되지 않는 방어는 방어가 아니다.**

`protect.py`와 `ws_server.py`가 이제 `build_ensemble()`을 쓴다.
ECAPA를 못 불러오면 단독으로 떨어지되 **경고를 낸다.** 단독이 전이되지
않는다는 것이 측정된 사실이라 모르고 쓰면 안 된다.

> 재현: `python eval_transfer.py`

### DSR 재측정 — 앙상블이 실제 복제를 밀지만, 아직 못 막는다

XTTS-v2로 실제 복제를 돌려 원본 화자와 비교했다(조건당 5회, `eval_dsr.py`).

| 보호 방식 | 복제 대상 | Resemblyzer | ECAPA-TDNN | 저지율 |
|---|---|---:|---:|---:|
| — | **원본** (기준선) | 0.9336 ±0.0060 | 0.8009 ±0.0192 | 0% |
| 단독 | 보호본 | 0.9212 ±0.0065 | 0.7667 ±0.0218 | 0% |
| 앙상블 | **보호본** | **0.9010** ±0.0093 | **0.6766** ±0.0237 | 0% |

**기준선이 임계값(0.7962) 위다.** 원본 복제가 Resemblyzer 0.9336이므로
XTTS는 이 목소리를 제대로 복제한다 — 이 측정은 성립한다.

읽을 것이 셋이다.

**① 앙상블이 단독보다 확실히 낫다.** ECAPA 기준 0.7667 → 0.6766이고,
신뢰구간이 겹치지 않는다. 전이성 개선이 인코더 비교에서만이 아니라
**실제 복제음에서도** 나타났다. 이게 이번 작업의 성과다.

**② 그런데 저지율은 여전히 0%다.** ECAPA는 임계값 아래로 내려갔지만
Resemblyzer가 0.9010으로 높게 남았다. 저지는 **두 인코더 모두** 아래여야
인정하므로 0%다. 한쪽만 보면 "50% 달성"이라고 쓸 수 있지만 그건
이번에 고친 바로 그 잘못이다.

**③ 원본 대비 하락폭이 작다.** 0.9336 → 0.9010, 0.0326이다.
같은 파일을 두 번 복제해도 유사도가 0.019 차이 나므로, **생성의 무작위성과
같은 자릿수**다. 신뢰구간은 겹치지 않지만 실용적 의미는 아직 없다.

### 하마터면 정반대로 보고할 뻔했다

첫 채점에서 이런 값이 나왔다.

```
원본 복제    Resemblyzer 0.5664   ECAPA 0.1209   저지 100%
보호본 복제  Resemblyzer 0.5887   ECAPA 0.1010   저지 100%
```

"DSR 0% → 100%"로 읽힌다. **전부 틀린 값이었다.**
XTTS-v2는 24 kHz로 출력하는데 16 kHz로 읽고 있었다 —
음높이와 속도가 1.5배 어긋난 채로 채점됐다.

살아난 것은 **기준선을 먼저 보는 규칙** 덕분이다.
원본 복제조차 "저지"로 나오는 것은 방어가 통한 것이 아니라
복제가 애초에 안 됐거나 측정이 틀렸다는 뜻이다.
`Verify.tsx`에 그 검사를 넣어 둔 것이 여기서 값을 했다.

### 인코더 셋 — 같은 패턴이 세 번째로 반복됐다

Resemblyzer가 0.90으로 버티므로 셋째 인코더를 붙였다.
**WavLM-SV**(Microsoft · 자기지도 트랜스포머)를 골랐다 —
앞의 둘과 겹치는 곳이 가장 적다.

| | Resemblyzer | ECAPA-TDNN | WavLM-SV |
|---|---|---|---|
| 구조 | 3층 LSTM | TDNN + SE-Res2Block | 트랜스포머 12층 |
| 특징 | 선형 mel 40 | log fbank 80 | **원시 파형** |
| 학습 | 지도 (GE2E) | 지도 (VoxCeleb) | 자기지도 후 미세조정 |

**특징 추출부터 다르다.** WavLM은 mel을 거치지 않으므로,
mel 영역에서만 통하는 섭동은 여기서 걸러진다.

8초 발화 · 통화 채널 통과 후:

| 앙상블 | Resemblyzer | ECAPA | **WavLM** | 소요 |
|---|---:|---:|---:|---:|
| 2개 · 40스텝 | 0.7780 ✓ | 0.5094 ✓ | **0.9620 ✗** | 19초 |
| 3개 · 40스텝 | 0.8162 ✗ | 0.4855 ✓ | 0.4333 ✓ | 72초 |
| **3개 · 200스텝** | **0.6860 ✓** | **0.5962 ✓** | **0.4949 ✓** | 440초 |

**2개 앙상블이 WavLM에는 0.9620이다.** 거의 그대로 남았다.
단독→ECAPA에서 0.8131, 2개→WavLM에서 0.9620 — **붙이지 않은 인코더는
여전히 안 속는다**는 패턴이 세 번째로 반복됐다.

이것이 이 문제의 성질이다. 적대적 섭동은 **자기가 본 모델에만** 통한다.
"인코더를 하나 더 붙이면 되지 않을까"는 답이 아니다 —
네 번째 인코더도 같은 결과를 낼 것이다.

다만 **모아 놓으면 공통 방향이 생긴다.** 셋을 함께 밀자 200스텝에서
세 모델 모두 임계값 아래로 내려갔다. 서로 다른 세 구조가 동시에 틀리는
방향은 화자 정보 자체를 건드린다고 볼 근거가 된다.

대가는 시간이다. 8초 발화에 **440초**(CPU). 단독 40스텝의 5초에서 88배다.
GPU가 사실상 필수가 됐다.

> 재현: `python eval_ensemble.py` (STEPS 환경변수로 스텝 조절)

그리고 **WavLM은 복제음에서 0.9737로 꿈쩍도 하지 않았다.**
보호본 자체는 WavLM 0.4949까지 밀었는데도 그렇다.

### 왜 그런가 — 위협 모델과 최적화 대상이 어긋나 있었다

같은 파일을 채널 통과 여부만 바꿔 재보면 답이 나온다.

```
보호본 자체 vs 원본        WavLM 0.9372   ← 채널 통과 안 함
보호본(채널 통과) vs 원본   WavLM 0.4949   ← 채널 통과
보호본의 복제음 vs 원본     WavLM 0.9809
```

`channel_aware`가 기본값 True다. **전화망을 통과한 뒤의 신호**를 표적으로
최적화한다. 그래서 원본 파일 자체는 거의 안 건드려진 상태로 남는다.

그런데 복제 실험은 **원본 파일을 그대로** XTTS에 넣었다.
사기범이 보는 것은 채널을 통과하지 않은 파일이므로, 우리가 심은 섭동이
거의 없는 음성을 복제한 셈이다. **인코더를 몇 개 붙이든 결과가 같을 수밖에 없다.**

이건 성능 문제가 아니라 **설정이 서로 다른 두 위협을 섞은 것**이다.

| 위협 | 사기범이 얻는 음성 | 맞는 설정 |
|---|---|---|
| 통화를 녹음해 복제 | 전화망 통과 | `channel_aware=True` |
| 영상·파일에서 수집해 복제 | 원본 그대로 | `channel_aware=False` |

지금까지의 SRS 수치(0.37·0.49 등)는 전부 **첫 번째 위협** 기준이고,
DSR 측정은 **두 번째 위협** 조건에서 했다. 둘을 나란히 놓고 비교한 것이
잘못이었다.

### 다음에 할 일

1. `channel_aware=False`로 다시 보호본을 만들어 DSR을 잰다.
   **이게 진짜 대조 실험이다** — 지금까지 한 번도 맞춰 본 적이 없다.
2. 그래도 안 막히면, 표적을 화자 검증기가 아니라
   **XTTS 자신의 화자 조건화 경로**로 옮겨야 한다.
   검증기를 이기는 것과 생성기를 이기는 것은 다른 문제다.
3. 채널 통과 음성으로도 복제해 본다 — 첫 번째 위협의 DSR은 아직 모른다.

### 표적을 맞춰서 다시 쟀다 — 그래도 막지 못한다

`--raw-target`을 넣어 **원본 파일 자체**를 표적으로 최적화한 뒤 DSR을 다시 쟀다.
이제 최적화 조건과 복제 조건이 같다. 처음으로 맞춘 대조 실험이다.

| 보호 방식 | Resemblyzer | ECAPA | WavLM | 저지 |
|---|---:|---:|---:|---:|
| 원본 (기준선) | 0.9322 ±0.008 | 0.7880 ±0.018 | 0.9754 ±0.007 | 0% |
| 2개 (채널표적) | 0.9010 ±0.009 | 0.6766 ±0.024 | 0.9660 ±0.013 | 0% |
| 3개 (채널표적) | 0.9189 ±0.006 | 0.7158 ±0.025 | 0.9737 ±0.005 | 0% |
| **3개 (원본표적)** | **0.9048** ±0.010 | **0.6121** ±0.031 | **0.9431** ±0.019 | **0%** |

표적을 맞추니 세 인코더 모두 좋아졌다 — ECAPA 0.7158 → 0.6121,
WavLM 0.9737 → 0.9431. 방향은 확실히 맞다.

**그런데 저지율은 여전히 0%다.** 그리고 **WavLM이 0.9431로 거의 그대로다.**

### 진짜 결론 — 화자 검증기를 이겨도 복제는 막히지 않는다

네 조건에서 일관된 그림이 나왔다.

```
보호본 자체(원본표적, WavLM)     ~0.5 까지 내려간다
그 보호본으로 만든 복제음(WavLM)   0.9431 로 돌아온다
```

**섭동이 복제 과정을 통과하지 못한다.** XTTS는 참조 음성에서 자기 방식으로
화자 특징을 뽑고, 그 과정에서 우리가 심은 섭동이 씻겨 나간다.
리샘플링(16→24 kHz), 자체 특징 추출, 생성기의 사전확률이 모두 그렇게 작동한다.

인코더를 하나에서 셋으로 늘리고, 스텝을 40에서 200으로 올리고,
표적까지 맞췄는데도 DSR은 네 번 모두 0%였다.
**"화자 검증기를 속이면 복제도 막힌다"는 전제가 우리 측정으로는 지지되지 않는다.**

| 시도 | 결과 |
|---|---|
| 인코더 1 → 2 | ECAPA는 밀렸으나 DSR 0% |
| 인코더 2 → 3 | WavLM은 밀렸으나 DSR 0%, 오히려 나빠짐 |
| 40 → 200스텝 | DSR 0% |
| 채널표적 → 원본표적 | 세 인코더 다 개선, DSR 0% |

네 번 다른 축을 건드려 네 번 같은 답이 나왔다. 이건 조정으로 풀릴 문제가 아니다.

### 남은 길은 하나

표적을 **화자 검증기에서 생성기로** 옮겨야 한다.
XTTS의 화자 조건화 경로(speaker latent를 뽑는 부분)를 직접 공격하는 것이다.
검증기를 이기는 것과 생성기를 이기는 것은 다른 문제이고,
우리는 지금까지 전자만 해 왔다.

그건 이 대회 일정 안에 끝낼 수 있는 작업이 아니다.
**시연에서는 이 사실을 그대로 말하는 편이 낫다** — `DEMO.md` 씬 7이
이미 그렇게 쓰여 있다. 바꿀 것은 숫자뿐이다.

> 재현: `python protect.py <입력> -o out/raw3_200 --steps 200 --raw-target`
> 이어서 `python eval_dsr.py`

### 그래서 지금 정직한 결론

**모드 2는 아직 복제를 막지 못한다.** 여덟 달 전 측정(DSR 0%)과 결론이 같다.
달라진 것은 **왜 그런지 알게 된 것**과 **방향이 맞다는 증거를 얻은 것**이다.

- 원인 확정 — 인코더 하나에만 최적화했다(ECAPA 0.8131로 전혀 안 속았다)
- 방향 검증 — 앙상블로 ECAPA 0.7667 → 0.6766, 신뢰구간 분리
- 남은 벽 — 인코더를 셋으로 늘려도 DSR은 0%다. 오히려 2개보다 나빴다.
  원인은 **위협 모델과 최적화 대상의 불일치**였다(위 절 참조).
  `channel_aware=True`로 최적화한 파일을 채널 없이 복제했으니
  섭동이 거의 없는 음성을 복제한 셈이다. 맞춰서 다시 재야 한다.

### 아직 확인하지 못한 것

다음에 할 일은 정해져 있다.

1. **인코더를 더 붙인다** — 둘로는 부족하다는 것이 측정으로 나왔다.
   WavLM·TitaNet 계열을 더하면 Resemblyzer가 버티는 방향도 막힐 수 있다.
2. **스텝·세기를 올린다** — 지금은 40스텝·SNR 20 dB다. 다만 세기를 올리면
   들리기 시작하므로 청취 판단이 함께 가야 한다.
3. GPT-SoVITS·F5-TTS로 교차 확인 — 복제 모델 하나만 이기는 것도 같은 함정이다
4. 화자 수 늘리기 (지금 n=5·XTTS 합성 화자) — 사람 목소리로 재교정
5. RTX 장비에서 실행 — 앙상블은 CPU에서 4배 느리다

## 방향 전환 — 검증기가 아니라 복제기를 공격한다

네 축을 바꿔 가며 네 번 쟀는데 전부 DSR 0%였다. 그때 내린 결론이
"표적을 화자 검증기에서 생성기로 옮겨야 한다"였다. 그것을 했다
(`attack_cloner.py`).

### 표적

XTTS-v2는 참조 음성에서 **두 갈래**로 화자 정보를 뽑는다.

| 경로 | 무엇 | 쓰이는 곳 |
|---|---|---|
| `hifigan_decoder.speaker_encoder` | 512차원 화자 임베딩 (16 kHz) | 보코더 — **음색** |
| `get_gpt_cond_latents` | mel 기반 조건 잠재 (1024×T) | GPT — **말투·운율** |

둘 다 순수 torch 모듈이라 파형까지 역전파가 닿는다.
`@torch.inference_mode()`가 바깥 래퍼에 붙어 있어 `__wrapped__`로 벗기면 된다.
resnet 내부가 `squeeze_()`로 in-place를 쓰므로 입력을 복제해 넘겨야 한다.

**둘을 동시에 민다.** 음색만 밀면 GPT가 운율로 화자를 복원하고,
운율만 밀면 보코더가 음색을 복원한다 — 검증기 하나만 공격했을 때와 같은 실패다.

### 결과 — 30스텝으로 뒤집혔다

복제기 내부 조건(원본 대비 코사인):

```
       시작        30스텝 후
화자   +0.6875  →  -0.6282     ← 음수. 반대 방향을 가리킨다
운율   +0.4897  →  +0.1375
```

그 보호본으로 실제 복제한 음성을 세 인코더로 채점한 결과:

| 보호 방식 | Resemblyzer | ECAPA | WavLM |
|---|---:|---:|---:|
| 원본 (기준선) | 0.9307 | 0.8058 | 0.9676 |
| 검증기 공격 (인코더 3개·200스텝) | 0.9048 | 0.6121 | 0.9431 |
| **복제기 직접공격 (30스텝)** | **0.7035** | **0.0720** | 0.9403 |

**ECAPA 0.8058 → 0.0720.** 남남보다도 먼 값이다.
Resemblyzer도 0.7035로 임계값 아래로 내려갔다.
검증기를 200스텝 공격해 얻지 못한 것을 **직접공격 30스텝**이 해냈다.

### 복제를 막았다 — DSR 0% → 100%

150스텝으로 밀자 복제기 내부 조건이 **둘 다 음수**가 됐다.

```
       시작        150스텝 후
화자   +0.6875  →  -0.9111
운율   +0.4897  →  -0.1480
```

그 보호본으로 실제 복제한 음성:

| 보호 방식 | Resemblyzer | ECAPA | WavLM | **저지** |
|---|---:|---:|---:|---:|
| 원본 (기준선) | 0.9355 | 0.7879 | 0.9725 | 0% |
| 검증기 공격 (3개·200스텝) | 0.9048 | 0.6121 | 0.9431 | 0% |
| **복제기 직접공격 150스텝** | **0.6493** | **0.0495** | **0.8220** | **100%** |
| 직접공격 + 마스킹 150스텝 | 0.7906 | 0.1941 | 0.8531 | **80%** |
| (임계값) | 0.8090 | 0.5062 | 0.8773 | |

**다섯 번 복제 전부, 세 인코더 전부 임계값 아래다.** 기준선(원본 복제)은
셋 다 임계값 위이므로 이 측정은 성립한다.

### 들리지 않게 하는 대가

여기서 문제를 하나 찾았다. 직접공격은 **심리음향 마스킹을 쓰지 않았다.**
SNR만 맞추면 세기는 같아도 **들릴 자리**에 에너지가 몰린다.

| 조건 | SNR | 마스킹 위반 | 최대 초과 |
|---|---:|---:|---:|
| 검증기 공격 (마스킹 적용) | 20.04 dB | 3.2% | 10.2 dB |
| **직접공격 (마스킹 없음)** | 20.00 dB | **67.3%** | **52.4 dB** |
| 직접공격 + 마스킹 | 20.00 dB | 17.9% | 15.1 dB |

67.3%면 **들린다.** 같은 SNR인데 한쪽만 들리는 것은 위치가 다르기 때문이다.

마스킹 투영을 붙였다. 위반이 67.3% → 17.9%로 내려가고, **저지율은 100% → 80%**가 됐다.
방어와 청취의 정직한 교환이다 — 공짜가 없다.

| | 저지율 | 마스킹 위반 |
|---|---:|---:|
| 마스킹 없음 | 100% | 67.3% (들린다) |
| **마스킹 적용** | **80%** | **17.9%** |

발표에서는 **마스킹 적용본**을 쓰는 것이 맞다. 들리는 방어는 사용자가 끈다.

### GPT-SoVITS도 표적에 넣었다 — 그리고 또 같은 패턴이 나왔다

XTTS 하나만 막으면 그 모델에 대한 과적합이다. 검증기 쪽에서 세 번 겪은 일이라
복제기라고 다를 이유가 없었다. **GPT-SoVITS**(한국어 복제의 사실상 표준)를
두 번째 표적으로 붙였다.

| | XTTS-v2 | GPT-SoVITS |
|---|---|---|
| 음색 | HiFi-GAN 화자 인코더 (ResNet · **파형** 입력) | `ref_enc` MelStyleEncoder (**선형 스펙트로그램** 입력) |
| 표본화율 | 22.05 kHz | 32 kHz |

겹치는 곳이 거의 없다. 확인해 보니 예상대로였다.

```
보호본                    XTTS      GPT-SoVITS
XTTS만 표적            -0.8200      +0.8280   ← 전혀 안 밀린다
XTTS + GPT-SoVITS      -0.4650      +0.6492
```

**네 번째 반복이다.** 단독→ECAPA 0.8131, 2개→WavLM 0.9620,
검증기→복제기 0.9403, 그리고 XTTS→GPT-SoVITS 0.8280.
적대적 섭동은 **자기가 본 모델에만 통한다** — 예외가 없다.

### 45회로 되풀이해 보니 — 손잡이가 아니라 강건성이었다

한 번 통한 것은 우연일 수 있다. 조건을 45개로 늘려 되풀이했다.

| 묶음 | 무엇을 흔들었나 | 저지 |
|---|---|---:|
| A (8) | 스텝 100·150·250·400 / SNR 16·24 / 배율 2·4 | 5/8 |
| B (3) | 화자 3명 | 3/3 |
| C (4) | mp3 · 전화대역 · 잡음 · 3초 절단 | 2/4 |
| D (8) | 위에서 좋았던 값을 **합쳐** 강화 | 4/8 |
| **E·F·G (22)** | **EOT — 열화를 최적화 안으로** | **17/20** |

**실패한 5개가 전부 WavLM 하나만 임계값 위였다.** WavLM을 공격 표적에
넣으면 곧장 뚫리지만, 그러면 WavLM은 더 이상 독립된 심판이 아니다.
검증기 쪽에서 세 번 겪은 과적합이라 그 길은 닫아 뒀다.

대신 손잡이를 합쳐 봤다(D). **더 나빠졌다** — mp3가 0.8431에서 0.9010으로,
화자02가 0.8666에서 0.8934로 갔다. 100스텝은 막고 150스텝은 뚫리고
250스텝은 막았다. 단조롭지 않다.

그래서 진단을 바꿨다. **강도의 문제가 아니라 강건성의 문제다.**
깨끗한 파일에서만 최적화한 섭동은 전송을 거치면 씻겨 나간다.
그러면 열화를 손실 안으로 들여와야 한다 — EOT다.

```
매 스텝: 파형을 무작위로 한 번(때로 두 번) 망가뜨린 뒤 손실을 잰다
         전화대역 3.4 kHz · 잡음 SNR 20~30 · 무작위 절단 · mp3 근사 · 그대로
```

전부 미분 가능해야 해서 mp3는 대역제한 + 세기 양자화로 근사했다.

### EOT 결과 — 한 겹 열화까지 12/13

| 조건 | Resem | ECAPA | WavLM | 저지 |
|---|---:|---:|---:|:--:|
| 열화 없음 | 0.5903 | 0.1122 | 0.7816 | ○ |
| mp3 64 kbps | 0.6154 | 0.0960 | 0.7870 | ○ |
| 전화대역 8 kHz | 0.6631 | 0.2127 | 0.8052 | ○ |
| 잡음 SNR 20 | 0.6839 | 0.2645 | 0.7883 | ○ |
| 3초 절단 | 0.5735 | 0.0753 | 0.6821 | ○ |

EOT 이전에 뚫렸던 mp3·전화대역·잡음이 전부 막혔다.

### 그리고 뜻밖의 소득 — CPU에서 15초

GPT-SoVITS 단독 표적에 운율 가중치 0이면 **400스텝이 CPU에서 15초**다.
옛 설정(XTTS + GPT-SoVITS + 운율)의 80스텝 2~3분과 25배 차이다.
XTTS의 GPT 조건 잠재 경로가 비용의 대부분이었다.

이 덕에 **EXE 안에서도 진짜 방어 경로를 돌릴 수 있게 됐다.**
XTTS는 수 GB라 못 넣지만 GPT-SoVITS 표적은 `s2G488k.pth` 하나
(약 100 MB)면 되고, 첫 실행에서 내려받는다.

### 남은 한계 — 발표에서 반드시 말할 것

**화이트박스다.** 두 모델의 가중치를 갖고 공격했다.
사기범이 제3의 모델을 쓰면 그 모델의 `ClonerTarget`을 구현해야 한다.
위 표의 마지막 줄이 그 사실을 스스로 증명한다 —
XTTS만 막았을 때 GPT-SoVITS는 0.8280으로 멀쩡했다.

그리고 **화자 1명 · n=5**다. 사람 목소리로, 여러 화자로 다시 재야 한다.

정직한 표현은 이것이다 —
**"어떤 복제 모델을 막을지 알면, 막을 수 있다."**

### 임계값을 인코더마다 따로 쟀다

여기서 측정 오류를 하나 잡았다. 지금까지 `0.7962`를 세 인코더에 똑같이 썼는데,
그 값은 **Resemblyzer에서만** 잰 EER 지점이다. 인코더마다 유사도 분포가 다르다.

화자 6명·조각 35개로 다시 쟀다(`eval_thresholds.py`).

| 인코더 | 같은 화자 | 다른 화자 | **임계값** | EER |
|---|---:|---:|---:|---:|
| Resemblyzer | 0.8692 | 0.5991 | **0.8090** | 3.5% |
| ECAPA | 0.6802 | 0.1944 | **0.5062** | 3.4% |
| WavLM | 0.9278 | 0.6433 | **0.8773** | 15.4% |

WavLM은 다른 화자끼리도 0.64가 나온다. 그 척도에 0.7962를 쓰면
거의 모든 쌍이 "타 화자"가 되어 판정이 무의미해진다.

새 임계값으로 다시 채점하면 직접공격은 **3개 중 2개를 통과한다** —
Resemblyzer 0.7035 < 0.8090 ✓, ECAPA 0.0720 < 0.5062 ✓,
WavLM 0.9403 > 0.8773 ✗.

**저지율은 여전히 0%다**(셋 다 통과해야 인정). 다만 처음으로 두 개가 넘어갔고,
남은 것은 EER 15.4%로 셋 중 가장 판별력이 낮은 인코더 하나다.

## 실제 사람 목소리 · GPT-SoVITS 복제 저지 100%

프로젝트가 성공이라고 말하려면 이 문장이 서야 했다.

> **GPT-SoVITS에 원본을 주면 그 사람 목소리가 나오고,
> 보호본을 주면 다른 사람 목소리가 나온다.**

그동안 GPT-SoVITS는 **표적**으로만 썼다 — 섭동을 계산하려고 `ref_enc`를
불러왔을 뿐, 그 모델로 목소리를 만들어 본 적이 없었다. 실제 복제 검증은
전부 XTTS로 했다. **표적과 검증 모델이 달랐다.**

`clone_gsv.py`가 그 자리를 메운다. GPT-SoVITS의 음색 변환 경로를 그대로 쓴다.

```
내용(무엇을 말하나)   ←  고정된 원본 발화의 SSL 특징 (cnhubert)
음색(누구 목소리인가) ←  참조 음성의 ref_enc 벡터      ← 여기만 바뀐다
```

같은 내용을 **원본 참조**와 **보호본 참조**로 각각 만들어 비교한다.
음색 이외의 변수가 없어 두 결과의 차이는 오직 참조 음성 차이다 —
전체 추론을 쓰면 GPT의 무작위성이 섞여 원인을 말하기 어려워진다.

### 결과 — 팀원 실제 목소리

| 보호 방식 | Resemblyzer | ECAPA | WavLM | **저지** |
|---|---:|---:|---:|---:|
| 원본 참조 (기준선) | 0.8866 | 0.6510 | 0.9694 | 0% |
| 표적 3개(xtts·gsv·wavlm) 150스텝 | 0.8318 | 0.4626 | 0.9714 | 0% |
| **GPT-SoVITS 집중 250스텝** | **0.6701** | **0.0892** | **0.8445** | **100%** |
| 판정 기준선 | 0.8090 | 0.5062 | 0.8773 | |

**세 검증기 전부 임계값 아래다.** 기준선(원본 참조 복제)이 임계값 위이므로
이 측정은 성립한다 — GPT-SoVITS는 이 목소리를 제대로 복제한다.

복제기 내부 조건은 **+0.1743**까지 밀렸다(원본 1.0에서).

### 왜 집중이 통했나

표적을 셋으로 나눴을 때는 GPT-SoVITS 몫이 부족했다(저지 0%).
`--target gsv --prosody-weight 0`으로 **그 모델 하나에만** 예산을 쓰자 뚫렸다.

오늘 다섯 번 확인한 것과 같은 이야기다 — **적대적 섭동은 자기가 본 모델에만
통하고, 표적을 나누면 각자의 몫이 줄어든다.** 막을 모델이 정해져 있다면
그쪽에 집중하는 편이 낫다.

> 재현:
> ```
> .venv-xtts\Scripts\python attack_cloner.py 입력.wav -o out/gsv >     --target gsv --steps 250 --prosody-weight 0 --masking-ratio 3.0
> .venv-xtts\Scripts\python clone_gsv.py out/gsv/original.wav >     out/gsv/protected.wav -o out/gsv_clone
> python eval_dsr.py
> ```

### 남은 한계

**4단 겹침은 못 막는다.** mp3 → 전화대역 → 잡음 → 2초 절단을 한꺼번에
거치면 섭동이 사라진다. 다만 그 조건에서는 **원본조차 복제되지 않는다** —
네 번 중 두 번은 기준선이 임계값 아래로 떨어져 측정 자체가 성립하지 않았고,
나머지 두 번도 검증기 셋 중 둘이 이미 "다른 사람"이라고 답했다.
목소리를 그만큼 망가뜨리면 복제기도 쓸 게 없다는 뜻이지만,
**우리 방어가 거기까지 미친다고 말할 수는 없다.**

**화자 6명 중 1명(화자06)이 남았다.** Resemblyzer 0.8384로 임계값 0.8090을
근소하게 넘겼다. 겹침 EOT로도 이 화자는 못 넘겼다.

그리고 GPT-SoVITS의 **음색 경로**만 검증했다 —
전체 추론(GPT 단계 포함)은 텍스트 프런트엔드가 필요해 아직 안 돌렸다.
XTTS는 같은 보호본으로 재보지 않았다(집중 표적이라 안 밀릴 가능성이 높다).

## 실시간 섭동 주입 — 두 가지 방식을 재고 둘 다 접었다

복제를 막게 된 뒤 남은 질문은 하나였다. **통화 중에 실시간으로 넣을 수 있는가.**
통신사에 제안하려면 그게 필요하다는 요구가 있었고, 그래서 두 방식을 재봤다.
**둘 다 안 된다.** 실패도 기록으로 남긴다 — "재봤고 이래서 안 된다"가 있어야
제안서에서 방어된다.

### ① 사전 계산 섭동 — 잡음보다 못하다

실시간의 표준 해법은 "통화 중 최적화"가 아니라 **사전 계산 + 실시간 덧셈**이다.
등록 때 한 번 δ를 만들어 두고 통화 중에는 더하기만 한다. 그러면 GPU도 필요 없다.

여기엔 검증되지 않은 가정이 있었다 — **등록 때 읽은 문장과 통화 내용이 다르다.**
한 화자의 녹음을 앞뒤로 잘라, 앞(A)으로 만든 δ를 **한 번도 보지 않은 뒤(B)**에
얹어 봤다(`eval_universal.py`).

| 조건 | XTTS | GPT-SoVITS |
|---|---:|---:|
| B 원본 | 1.0000 | 1.0000 |
| **B + δ(A)** ← 사전 계산 | **0.9075** | **0.8620** |
| B + δ(B) ← 상한선 | −0.8324 | 0.6906 |
| B + 잡음 ← **하한선** | 0.7720 | 0.5963 |

**잡음보다 나쁘다.** δ가 그 발화의 파형에 맞물려 있어서, 다른 말을 하면
위상도 내용도 어긋난다.

> **내가 근거를 잘못 썼다.** "발췌 견고성"(2초를 잘라내도 0.82 유지)을
> 사전 계산이 될 근거로 들었는데, 그건 **같은 발화 안에서** 잘라낸 것이었다.
> δ가 그 파형과 정렬돼 있으니 당연했고, **다른 발화로 옮기는 것과는 다른 문제**다.

### ② 청크 스트리밍 — 창을 맞춰도 절반이다

남은 길은 짧은 지연을 받아들이고 그 구간을 즉석 최적화하는 것이다
(`eval_streaming.py`). 복제기 표적으로는 재본 적이 없었다.

| 버퍼 | 방식 | XTTS | GPT-SoVITS | 소요 |
|---|---|---:|---:|---:|
| — | 전체 일괄 (기준선) | −0.7961 | 0.5386 | 104초 |
| 2초 | 청크 독립 | −0.1470 | 0.6664 | 49초 |
| 2초 | 청크 + 공유 방향 | −0.1329 | 0.6792 | 53초 |
| — | 전체 일괄 (12초 입력) | −0.7956 | 0.7847 | 75초 |
| **6초** | 청크 독립 | **−0.4211** | 0.7869 | 58초 |
| 6초 | 청크 + 공유 방향 | −0.4160 | 0.7791 | 58초 |

**가설 하나는 맞고 하나는 틀렸다.**

- 맞음 — 복제기가 보는 창(XTTS 6초)보다 짧게 자르면 무너진다.
  2초에서 −0.147이던 것이 6초에서 −0.421로 회복됐다.
- **틀림** — "방향이 제각각이라 상쇄된다"고 보고 첫 청크의 δ를 물려줬는데
  −0.1470 → −0.1329로 **오히려 미세하게 나빴다.** 방향의 문제가 아니라
  **보는 범위의 문제**였다.

그리고 창을 맞춰도 전체 일괄의 **절반**이다. 시간 이득은 75 → 58초로 23%뿐이다.
**지연 6초를 감수하고 얻는 것이 그 정도다.** 6초 지연은 통화에 쓸 수 없다.

### 그래서 접었다

두 방식을 다르게 재서 둘 다 부정됐다. 세 번째를 찾기보다 되는 것을
제대로 만드는 편이 남은 시간에 맞다.

**모드 2의 형태는 "녹음 종료 즉시 보호"다.** 지금 앱이 하는 그대로이고,
실제로 복제를 막는다(저지 100%). 목소리가 **저장되는 지점**에 붙이면 된다 —
통화 녹음 부가서비스, 음성사서함, SNS 업로드 전. 셋 다 실시간이 필요 없다.

**통신사 제안의 축은 모드 1이다.** 발신번호 필터로 정밀도 14.6% → 77.7%.
그 필터를 걸 수 있는 것은 통신사뿐이고, 모드 1은 발화 단위라 이미 실시간이다.

> 통화 오디오를 실시간으로 변조하는 것은 기술이 되더라도
> 지연·품질·법규에서 먼저 걸린다. **약속하지 않은 것을 못 지키는 일은 없다.**

### 남은 측정 한계

이 결론은 **화자 1명 · 발화 2개**로 얻었다. GPT-SoVITS는 같은 전체 일괄인데도
발화에 따라 0.5386과 0.7847로 갈렸다 — 편차가 크다. 사람 목소리 여러 명으로
다시 재야 이 결론도 굳는다.

## 앱 모드 2에 직접공격 배선

앱은 그동안 **검증기 경로**(저지 0%)를 쓰고 있었다. 새 방식은 `attack_cloner.py`에
따로 있었고 환경도 갈려 있었다 — 복제 모델은 `.venv-xtts`, 서버는 `.venv`.

`.venv-xtts`에 서버 의존성(websockets·faster-whisper·resemblyzer·webrtcvad·
speechbrain)을 설치해 **한 환경에서 다 돌게** 합쳤다.

```bash
.venv-xtts\Scripts\python ws_server.py --cloner xtts,gsv --steps 150 --time-budget 300
```

`--cloner`를 주면 보호 경로가 복제기 직접공격으로 바뀐다. 비우면 옛 검증기
경로로 돌되 **시작할 때 경고를 낸다** — 그 경로가 실제 복제를 막지 못한다는 것이
측정된 사실이라 모르고 쓰면 안 된다.

화면에 뜨는 SRS의 **의미가 달라진다.** 검증기 경로에서는 화자 검증기의 유사도이고,
직접공격에서는 **복제기 내부 화자 조건**의 유사도다. 후자가 실제 복제 결과와
직결되므로 판정 임계값도 따로 둔다(`CLONER_COND_THRESHOLD = 0.30` —
실측에서 이 아래일 때 저지율 100%였다). 표적이 여럿이면 **가장 덜 밀린 쪽**을
대표값으로 쓴다. 하나만 막고 나머지가 남으면 방어가 아니다.

### 종단 확인 — 통과했다

앱이 보내는 것과 **똑같은 메시지 순서**로 서버를 왕복시켰다
(`start(protect)` → `audio` 헤더 → PCM → `progress`×N → `done` → δ 바이너리).

```
[완료] srs -0.6672 · 기준 "복제기 내부 화자 조건 (xtts-v2)"
       snr 20.00 dB · elapsed 26.2초 · audible_violation 0.1772
       below_threshold True
[바이너리] delta 80000 vs 원본 80000 → 일치 · 총 41초
progress 40회 · 마지막 (40, 40)
```

5초 입력 · 40스텝 · CPU 기준이다. SRS가 **음수**인 것이 핵심이다 —
복제기 내부에서 원본과 반대 방향을 가리킨다는 뜻이고, 실측에서 이 상태의
저지율이 100%였다.

**고친 결함 둘이 여기서 나왔다.**

1. `CLONER_COND_THRESHOLD`가 정의되지 않은 채 참조되고 있었다.
   보호는 끝나는데 `done`을 만들 때 터져서 **앱에는 오류만 보였다.**
2. 진행 콜백이 배선되지 않아 `progress`가 **0회**였다.
   앱 진행 막대가 40초 동안 멈춰 있어 죽은 것처럼 보인다.
   `attack()`에 `on_step`을 넣어 스텝마다 올린다.

둘 다 코드를 읽는 것만으로는 안 나오고 **실제로 돌려야 나오는** 종류다.

앱 화면(`딥보이스 방지` 탭)도 정상 렌더링을 확인했다.
브라우저에 마이크가 없어 녹음 자체는 못 돌렸지만, 녹음 뒤 서버로 가는
경로는 위 왕복이 그대로 증명한다.

## 실사용 설정 — 앙상블을 켜면 앱이 멈춘다

인코더를 늘린 대가가 시간이다. 8초 녹음에 CPU로 440초 —
서버를 그대로 두면 **앱이 멈춘 것처럼 보인다.**

`ws_server.py`에 둘을 넣었다.

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--time-budget` | 90초 | 보호 1건에 쓸 최대 시간. 넘기지 않게 스텝이 자동으로 줄어든다 |
| `--encoders` | 2 | 1=Resemblyzer · 2=+ECAPA · 3=+WavLM |

실측 — 200스텝을 요청해도 예산에 맞춰 줄어든다.

```
[ready] steps 200 · threshold 0.7962
[완료] srs 0.6574 (통화 채널 통과 후) · snr 20.03 dB · elapsed 90.1초
```

**기본값을 3개가 아니라 2개로 둔 이유가 있다.** DSR은 어느 값이든 0%다.
인코더를 늘려 얻는 것은 *측정되는 SRS 하락*이지 *실제 방어*가 아니다.
그렇다면 시연에서 쓸 수 없을 만큼 느려지는 쪽을 기본값으로 둘 이유가 없다.
연구용으로 3개가 필요하면 `--encoders 3`으로 켠다.

## 정직성에 관한 메모

이 프로젝트는 "공격 사슬의 비어 있는 앞단에 방어를 배치하고,
그것이 실제로 어디까지 작동하는지를 **정직하게 측정하는** 시도"로 스스로를 규정했다(D07 §07).

현재 측정 결과는 방어가 XTTS-v2 복제를 막지 못한다는 쪽이다.
이 숫자를 숨기고 발표하면 프로젝트의 존재 이유 자체가 무너진다.
부정적 결과는 그대로 싣고, **왜 안 되는지를 정량적으로 설명하는 것**이 기여다.
