하나의 앱, 두 개의 모드

모바일 앱에 두 기능을 담는다. 모드 1은 말하는 내용을 실시간으로 분석해 보이스피싱 위험을 경고하고, 모드 2는 녹음과 동시에 적대적 섭동을 주입해 딥보이스 학습을 막는다. 둘 다 한 사람이 앱에 대고 말하는 구조이므로 통화 지연 제약을 받지 않는다.

01 · 문제

방어는 전부 뒤쪽에 몰려 있다

보이스피싱 방어는 모두 통화가 시작된 뒤에 작동한다. 그런데 공격은 그보다 앞, 목소리를 가져가는 순간 이미 시작되어 있다. 공격 사슬 1~2단계(음성 수집·복제)에는 방어가 없다.

1음성 수집없음 — 완전 공백모드 2

탐지를 더 잘 만드는 것으로는 안 되는 이유

탐지는 이미 만들어진 가짜 목소리를 판별한다. 즉 복제가 성공한 뒤에 개입한다. 사전 방어는 복제 자체를 실패시킨다. 개입 시점이 다르므로 두 방식은 경쟁이 아니라 서로 다른 층위다. 탐지는 위조지폐 감별기이고 사전 방어는 위조 방지 기술이다 — 둘 다 필요하다.

1.1딥보이스가 무너뜨린 것

딥보이스 이전에는 사기범이 왜 목소리가 다른가를 설명해야 했다. “휴대폰이 고장났다” 같은 변명이 그것이다. 그런데 그 변명은 동시에 피해자가 의심할 수 있는 단서이기도 했다. 딥보이스는 이 단서를 제거한다. 교육은 단서를 알아보는 능력을 기르는 것인데, 단서 자체가 사라졌다.

02 · 구성

두 모드

MODE 1 · 보이스피싱 위험 경고

가해자 발화 분석

  • 누가 말하나 — 사기범 역할
  • 동시에 무엇을 — 녹음 + 위험도 분석
  • 결과물 — 경고 음성 + 위험 등급
  • 분할 — VAD 발화 단위 (문장 경계)
  • 지연 — 발화 종료 후 약 0.7초
  • 부가 — 딥보이스 탐지 (P1)
MODE 2 · 딥보이스 학습 방지

적대적 섭동 주입

  • 누가 말하나 — 보호받을 사람
  • 동시에 무엇을 — 녹음 + 섭동 주입
  • 결과물 — 보호된 음성 파일
  • 분할 — 고정 2.0초 · 50% 겹침
  • 지연 — 발화 종료 후 약 0.5초
  • 강도 — PGD 200스텝 (표준의 2배)
이 구조가 해소한 제약

둘 다 대화 상대가 없는 단일 화자 녹음이다. ITU-T G.114의 편도 400 ms 기준은 두 사람이 실시간으로 주고받을 때 적용되는 것이므로, 이 구조에는 적용되지 않는다. 덕분에 모드 2가 PGD 풀 강도를 그대로 쓸 수 있다. 양방향 통화였다면 UFP 사전패치로 방어를 크게 낮춰야 했다.

2.1두 모드는 동시에 돌지 않는다

사용자가 탭을 골라 쓰므로 자원 경합이 없다. 시연에서도 각각 따로 보여준다 — 모드 2로 보호한 음성을 모드 1의 딥보이스 탐지기에 넣으면 “가짜”로 판정될 수 있어 설명이 꼬인다. 적대적 섭동은 탐지기가 찾는 바로 그 종류의 인공물이기 때문이다. 이 상호작용은 한계로 명시한다.

03 · 아키텍처

모바일 앱 + 서버 백엔드

폰에서 PGD를 돌릴 수 없다 — 두 가지 이유

① 연산량 — 2초 청크 200스텝이 RTX 3060에서 0.36초인데, 플래그십 폰 GPU에서는 7.3초다. hop 1.0초마다 청크가 발생하므로 적체가 무한히 쌓인다.
② 역전파 미지원 — CoreML · TFLite · ONNX Runtime Mobile은 추론만 지원한다. PGD는 gradient가 필수다. 이건 FLOPS 이전의 구조적 문제이며, 성능이 좋아져도 해결되지 않는다.

2초 청크는 16 kHz 모노 16 bit로 64 KB다. 어느 회선에서든 1초 이내이며, 시연은 같은 WiFi에 서버를 두므로 0.5초다. 온디바이스(불가능)와 실질적 차이가 없다.

3.2앱 형태 — 모바일 웹앱(PWA)

형태추가 인시평가
네이티브 Android + 온디바이스 STT+38개인정보 주장은 유지되나 3주에 과하다
모바일 웹앱(PWA) + 서버 처리+15채택 — MediaRecorder API로 마이크 접근, iOS·Android 공통. 전체화면 실행 시 네이티브와 구분되지 않는다
PWA + WASM 온디바이스 STT+24절충안이나 WASM Whisper 성능이 불확실하다
개인정보 — 정직하게 서술한다

기존 문서는 “Whisper 로컬 처리로 통화 내용이 단말을 떠나지 않는다”를 모드 1의 차별점으로 삼았다. 서버 처리로 구현하면 이 주장은 본 MVP에 대해서는 성립하지 않는다.

정확한 서술 — “본 MVP는 서버 처리로 구현했다. 상용화 시 whisper.cpp 온디바이스 전환으로 통화 내용이 단말을 떠나지 않게 하는 것이 로드맵이며, 이는 검증된 경로다.” 모드 2는 본인 음성을 본인 동의로 처리하므로 서버 전송에 문제가 없다.

촬영 조건

서버를 같은 WiFi의 노트북에 두고 폰을 연결한다. 외부 네트워크 의존을 제거하면 실패 요인이 하나 줄어든다. 화면 녹화(iOS·Android 기본 기능)로 폰 화면을 담고, 실물 촬영을 겹쳐 편집한다. 3회 이상 리허설하고 성공 테이크를 미리 확보한다.

05 · 일정

3주 계획

D1–D2

리스크 스파이크

XTTS-v2 설치·실행, 화자 인코더 gradient 접근 확인, 오프라인 보호 파일 1개로 복제 실패 검증. 동시에 폰 브라우저에서 MediaRecorder + WebSocket이 동작하는지 확인한다.

게이트 — 복제 실패 미확인 시 파라미터 재조정 · XTTS 실패 시 OpenVoice v2 전환
W1

서버 코어 + 대조군

PGD 본체(정규화 순서·NaN 방지·마스킹 투영), 단위 테스트 3건을 구현 첫날 작성. 팀원 음성 n≥30 확보. 대조군 C-A/C-B/C-E를 이 주에 반드시 돌린다 — 4시간이면 끝난다. 병행해 패턴 DB 182항 작성(작성자 분리).

W2

스트리밍 + 스코어러

WebSocket 청크 스트리밍, 서버 워커 큐, overlap-add 조립. 모드 1의 VAD 발화 분할·누적 전사 버퍼·스코어러+라우터. 경고 TTS 뱅크 사전 생성.

W3

모바일 UI · 통합 · 촬영

PWA 셸(녹음 컨트롤·파형·설정)과 두 모드 화면, 경고 재생. 딥보이스 탐지 연동(여건 시), 시연 영상 촬영, 보고서. 부정적 결과도 그대로 싣는다.

07 · 경계

주장할 수 있는 것과 없는 것

주장할 수 있다
  • 공격 사슬 1~2단계에 방어를 배치하는 국내 첫 시도
  • 모바일에서 녹음과 동시에 섭동을 주입 — 발화 후 0.5초
  • 피해자의 판단을 요구하지 않는 방어 구조
  • 심리 기제에서 역산한 경고 설계 — 탐지가 아니라 개입을 다룬 드문 시도
  • 대조군을 포함한 방어 효과 측정
  • 통화 코덱 환경에서의 유효성을 정량 측정한 데이터
주장할 수 없다
  • “보이스피싱을 근절한다” · “모든 딥보이스를 막는다”
  • “범용 방어를 구현했다” — 측정하지 않은 모델에 대해서는 말하지 않는다
  • “통화 내용이 단말을 떠나지 않는다” — 본 MVP는 서버 처리다
  • “온디바이스로 동작한다” — PGD는 모바일 런타임에서 원리적으로 불가
  • 양방향 실시간 통화에서의 보호
  • 적응형 공격자(정화 공격) 하에서의 유효성
포지셔닝 한 문장

본 프로젝트는 “보이스피싱을 탐지하는 시스템”이 아니라, 공격 사슬의 비어 있는 앞단에 최초로 방어를 배치하고, 그것이 실제로 어디까지 작동하는지를 정직하게 측정하는 시도다. 탐지 영역은 통신사가 이미 높은 수준으로 점유했다. 우리가 할 일은 아무도 지키지 않는 지점을 지키는 것이다.
